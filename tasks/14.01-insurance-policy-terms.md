**Codex P1, and it must precede adequacy (14.2): adequacy computed from `sumAssuredPaise` alone is too shallow for Indian health insurance and produces dangerously optimistic conclusions.** A ₹10L floater with a 1% room-rent cap and a 20% co-pay is not ₹10L of usable cover.

The current `insurancePolicies` model has none of: deductible, co-pay, room-rent or ICU limits, disease sub-limits, waiting periods (initial, pre-existing, maternity), restoration benefit, no-claim bonus, employer-versus-personal ownership, network/TPA contacts, exclusions, nominee relationship, or covered-member identity — `coveredMembers` is a bare `text[]`, now linked to real people by 2.1.

Add structured terms, and a **claim-readiness checklist**: policy document present, health card, TPA contact, renewal current, waiting periods elapsed, disclosures complete. The moment a claim is needed is the worst possible time to discover a missing document or an unelapsed waiting period.

## Acceptance criteria
- [x] Structured terms: deductible, co-pay, room-rent/ICU limits, sub-limits, waiting periods, restoration, NCB
- [x] Employer-owned versus personal cover distinguished — employer cover ends with the job

## Implementation notes

- 19 new columns on `insurancePolicies` (migration `0026`): `ownership`/`employerName`,
  `deductiblePaise`, `coPayBps`, `roomRentLimitPaise`/`Bps`, `icuLimitPaise`/`Bps`,
  `subLimits` (jsonb `{label, capPaise}[]`), `initialWaitingDays`,
  `preExistingWaitingMonths`, `maternityWaitingMonths`, `restorationBenefit`,
  `ncbBps`/`ncbMaxBps`, `tpaName`/`tpaContactPhone`, `exclusions`, `disclosuresComplete`.
  All health-only numeric fields are nullable and Zod-gated to `kind: "health"`
  (`checkPolicyConsistency` in `packages/shared/src/schemas/insurance.ts`) — null
  means "not applicable to this policy kind", not "zero".
- `coveredPersonIds` (→ `family_members`) and `nomineePersonId` already existed
  from 13.7 and needed no changes — person-linkage was already real, not name strings.
- New pure module `services/claim-readiness.ts`: `computeWaitingPeriodEndDates`
  (startDate + days/months, month-end-clamped) and `computeClaimReadiness` (the
  checklist, health-only items omitted rather than false-failed for life/vehicle).
  Both DB-free per TDD.md's functional-core pattern; `insurance.ts`'s `toPolicy`
  wires them in with `today = todayInIST()`.
- UI for these fields is out of scope here — lands in 14.5 (protection-surface-ui).

## Codex review fixes (round 2)

A follow-up Codex review of the first pass found the update path had a real
data-loss bug plus incomplete gating, both fixed before merge:

- **P1 — editing a policy via the (pre-14.5) web form silently erased every
  new field.** `UpdateInsurancePolicySchema` defaulted every omitted field,
  and the form doesn't send the 19 new ones. Fixed by giving the update
  schema `.optional()` (no-default) overrides for the new fields — an
  omitted field means "leave unchanged," not "reset" — and having
  `updatePolicy()` strip `undefined` entries before the SQL `SET`.
- **P2 — incomplete health-only gating** (`subLimits`, `restorationBenefit`,
  `ncbBps`/`ncbMaxBps`, `tpaName`/`tpaContactPhone` weren't Zod-gated to
  `kind: "health"`) and **stale values on a kind/ownership change within the
  same request that omits the health/employer fields** (the Zod layer can't
  validate a merge against the untouched DB row). Fixed by extending the
  gating, and by having `updatePolicy()` force-clear health-only fields /
  `employerName` server-side whenever the *effective* kind/ownership (this
  request's, else the existing row's) rules them out — regardless of
  whether this request mentions them.
- **P2 — a null renewal date always read as "current"**, even for a
  recurring-premium policy that simply never had one entered. Fixed:
  `premiumFrequency` now gates it — null is only current for `"single"`.
- **P2 — TPA readiness ignored the contact phone**, and a positive waiting
  period with no policy start date produced `"Waiting period runs to null"`.
  Both fixed with the specific missing artifact named in each case.
- **P2 — zero-vs-unset waiting periods were inconsistent** between the two
  functions. `computeWaitingPeriodEndDates` now returns `null` for `<= 0`
  the same way `computeClaimReadiness` already omitted the item.

All fixes verified with a bite-check (revert → test fails → restore → test
passes) for the P1 fix, plus new unit coverage for each P2.
