**Fixes the dependency inversion Codex identified**: the deduction basket needed the regime comparison, which needed the basket. Extracting the rule data and the regime *preference* breaks the cycle — everything else in this phase reads from here.

Versioned, **effective-dated** rule data (extending the 4.2 registry rather than starting a second one):
- slabs for both regimes, rebate (87A), surcharge, cess, marginal relief
- standard deduction per regime
- deduction caps: 80C ₹1.5L, 80CCD(1B) ₹50k, 80CCD(2), 80D limits incl. senior-citizen and preventive-check-up sub-limits
- capital-gains rates, exemption thresholds and holding-period definitions
- advance-tax instalment percentages and due dates, 234B/234C rates

Plus a **user regime preference** — chosen, or inferred from payslip TDS — which gates whether deduction guidance is meaningful at all.

**Effective dates, not just financial years.** `tax-lots.ts` already encodes the 23 July 2024 holding-period reform and a section 50AA acquisition-date condition. Rules change mid-year and can depend on acquisition versus transfer date; an FY-keyed table cannot express that safely.

## Acceptance criteria
- [ ] All rates, caps and thresholds as effective-dated data — no inline constants anywhere in services
- [ ] Separate acquisition / transaction / assessment applicability where they differ
- [ ] User regime preference stored, with inference from payslip TDS as a fallback
- [ ] A missing rule for a date fails loudly; never silently falls back to a neighbouring year
- [ ] Historical FYs representable, so prior-year figures stay reproducible
- [ ] typecheck + lint + test green
