## Errors Found and Fixed

### TypeCheck Errors (2)

**Error 1** — `payslips.ts:150`: Property `errors` does not exist on `ZodError`

ZodError uses `.issues`, not `.errors`. The prior agent used the wrong property name.

```
Before: fyResult.error.errors[0]?.message ?? "Invalid fy"
After:  fyResult.error.issues[0]?.message ?? "Invalid fy"
```

**Error 2** — `payslips.ts:346`: Property `displayName` does not exist on `userProfiles`

The `loadUserIdentity` helper tried to select `userProfiles.displayName` but `userProfiles` only has `userId`, `dateOfBirth`, `createdAt`, `updatedAt`. The `displayName` field lives on the `users` table in `db/core-schema.ts`.

Fix: rewrote `loadUserIdentity` to query `users.displayName` and `users.email` from `core-schema.ts`, which also improves PII redaction by including the user's email address.

```typescript
// Before (wrong table):
const { userProfiles } = await import("../../system/schema.ts");
const [profile] = await db.select({ displayName: userProfiles.displayName })
  .from(userProfiles).where(eq(userProfiles.userId, userId));
return { names: profile?.displayName ? [profile.displayName] : [], emails: [], upiIds: [] };

// After (correct table):
const { users } = await import("../../../db/core-schema.ts");
const [user] = await db.select({ displayName: users.displayName, email: users.email })
  .from(users).where(eq(users.id, userId));
return { names: user?.displayName ? [user.displayName] : [], emails: user?.email ? [user.email] : [], upiIds: [] };
```

### Architecture Fix (not a compile error but a violation)

The route imported `mailboxSecret` from `../../ingest/services/mailboxes.ts` — a cross-module import the tax module has no business making. The function is a one-liner returning `config.MAILBOX_SECRET || config.SESSION_SECRET`. Removed the import and inlined the expression directly:

```
Before: secret: mailboxSecret(app.config)
After:  secret: app.config.MAILBOX_SECRET || app.config.SESSION_SECRET
```

### Backup Coverage Fix

`payslips.document_key` stores opaque object-storage keys for uploaded payslip documents and must be in `FILE_COLUMNS` for orphan detection and per-user archive cleanup. The prior agent added `payslips` and `payslip_components` to ALL_TABLES/USER_TABLES/LINKED_TABLES but missed FILE_COLUMNS.

The backup test's column-name scanner only looked for `stored_path` and `document_path`; `document_key` is a different naming convention. Added `document_key` to both:
1. `FILE_COLUMNS` in `backup.ts`
2. The column-name scan in `backup.test.ts` (so the drift test catches future tables that name their key column `document_key`)

## Unresolved Risks

1. **`document_key` naming convention**: The `payslips.document_key` column uses a different naming convention than the existing `stored_path`/`document_path` pattern. I updated the backup test's column-name scanner to also recognize `document_key`, which is correct for this table but means future tables storing object keys must also be named `document_key` (or `stored_path`/`document_path`) to be auto-detected. If a future table names its storage key column something else (e.g. `file_path`, `s3_key`), the backup test won't catch it.

2. **Vision path for PDF**: The route accepts PDFs (up to 20 MB) but the vision path (`ai.chat` with image blocks) only works for image types. A PDF passed to the vision path would fail at the provider because providers don't accept `application/pdf` as an image media type. The route guards this implicitly (vision path only triggers if `extractedText` is absent and `visionConsent=true`) but there is no explicit rejection when content-type is `application/pdf` and the text path fails. This is an edge case noted for future hardening.

3. **`payslip.document_key` not yet written**: The parse route currently does NOT store the uploaded file in object storage and populate `document_key`. The field exists in the schema and FILE_COLUMNS for future use. The vision path stores the file transiently and deletes it immediately after the model call.
