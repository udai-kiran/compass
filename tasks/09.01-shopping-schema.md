New `shopping` module — the first domain built natively on the Phase 1 module pattern rather than migrated onto it.

Tables: `shopping_lists`, `shopping_list_items`, `catalog_items`, `price_sources`, `price_observations`, `pantry_items`, `cart_drafts`, `habit_profiles`. Contracts go in a new `packages/shared/src/schemas/shopping.ts`, which slots into the already domain-grouped schemas folder.

Pantry and habit data are **household-scoped** (a household consumes as one unit), which is why this depends on the sharing guard rather than plain `user_id` scoping.

## Acceptance criteria
- [x] All 8 tables added, with `ALL_TABLES`/`USER_TABLES` updated in the same change
- [x] Prices stored as integer paise; quantities carry an explicit normalized unit
- [ ] Pantry and habit rows resolve through `withSharing()`, not raw `user_id`
      — **NOT DONE, deliberately.** `withSharing()` has zero importers and zero tests, and
      `POST /api/sharing-grants` cannot mint a grant for a shopping resource type, so a
      sharing-aware read would return exactly the owner's rows — identical behaviour, plus an
      unexercisable SQL branch. Blocked on the sharing rollout (grant-creation ownership
      verification + enum labels + applying the guard consistently across domains), which four
      other modules also await and which has no tracked owner. Owner-only scoping is in place with
      a documented single-point `SHARING SEAM`. See
      [`tasks/063-shopping-schema/TASK.md`](./063-shopping-schema/TASK.md).
- [x] Zod contracts in `packages/shared`, consumed by both API and web
- [x] Registered as a prefixed module plugin; route snapshot updated deliberately
- [x] typecheck + lint + test green
