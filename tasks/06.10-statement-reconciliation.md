A credit-card statement re-lists the whole cycle, but most of those lines already
arrived in real time as `transaction_alert` emails and were reviewed, categorized,
and accepted into the ledger. Processing the statement must not re-book them.

## Phase 1 — match & suppress (done)
- **Matcher** (`extractor/extract.ts`, `matchLinesToLedger`, pure/tested): exact
  signed amount + a date window, merchant text only breaking ties, mutual-best
  1↔1 so ambiguous pairs are left for review. Straddle-safe — it compares each
  line to the ledger by the line's own date ± window, never the statement period,
  so a near-close spend that bills next cycle isn't force-matched here; it carries
  forward and matches the statement that lists it.
- **Suppress, don't drop**: a matched line is saved as status `duplicate` with a
  `matched_transaction_id` link (migration 0038 + enum value). Hidden from the
  pending queue but kept and reversible.
- **UI**: the inbox shows a collapsed "N already in your ledger" group; "Not a
  duplicate" (`POST /api/inbox/:id/unmatch`) sends one back to pending.

## Phase 1.5 — timestamp matching (done)
Statements (and live alerts) print a per-transaction time; matching on it is far
stronger than fuzzy merchant + a date window.
- **Capture**: extraction now pulls a `time` per line; `istTimestamp()` combines
  date + time as IST into an instant, stored on `extracted_transactions.occurred_at_ts`.
- **Retain**: accept carries that instant to a new `transactions.occurred_at`
  (nullable; `date` stays authoritative). CSV/manual rows stay date-only.
- **Match**: when both a line and a ledger row carry a timestamp, it's the primary
  key — within `STATEMENT_MATCH_TIME_TOLERANCE_MS` (2 min) they lock and outrank
  any fuzzy candidate; beyond it they're treated as distinct spends and never
  paired (this is what separates two same-amount, same-day transactions). Falls
  back to the date-window + merchant score when either side lacks a time.
- Only forward-looking: existing ledger rows backfill `occurred_at` = NULL, so the
  lock engages once post-deploy alerts are accepted with their times.

## Phase 1.6 — statement summary & reward capture (done)
The transaction pass skips the statement's summary block (totals + reward points);
this adds a separate best-effort pass over it (`extractStatementSummary`) that
returns `{ totalDuePaise, minDuePaise, statementDate, rewards }`. Failure returns
null and never sinks the transaction extraction. Phase 2 reuses it for reconcile
totals.
- **Rewards**: `reward_entries` gains a nullable `ingestion_id`. On statement
  processing, `applyStatementRewards` replaces this ingestion's prior reward rows
  (replay-safe) and writes earned/redeemed deltas plus a reconciling adjustment so
  the card's running sum (its displayed balance) lands on the statement's closing
  balance — self-healing across a missed statement or a drifted manual entry
  (`computeStatementRewardEntries`, pure/tested). Migration 0040.

## Phase 2 — reconcile & clear (todo)
- A reconciliation record per (card, period) + `transactions.reconciled_statement_id`
  (set-once, idempotent on replay).
- "Review & clear" view: stamp the cycle's matched transactions settled, show the
  statement-total-vs-matched delta, and surface unreconciled exceptions
  (distinguishing "near close, bills next cycle" from a real miss).
- Match-driven, not date-driven: a transaction is cleared only when a statement
  line actually matches it.

## Acceptance criteria
- [x] Statement lines already in the ledger don't create pending drafts
- [x] Nothing is silently dropped — matches are linked and reversible
- [x] Boundary/straddle spends aren't force-matched to the wrong cycle
- [ ] (Phase 2) Cycle transactions can be marked reconciled/cleared by a statement
