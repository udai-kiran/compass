The revised plan is not implementation-ready. Three High-severity blockers remain.

## High

- **H3 remains invalid: `transactions.type` does not exist.** The proposed query uses `ne(transactions.type, "opening_balance")` in [TASK.md](/work/personal/compass/tasks/092-scheme-limits/TASK.md:120), but the `transactions` table has no `type` column or transaction-type enum in [ledger.ts](/work/personal/compass/apps/api/src/db/shared/ledger.ts:22). Opening balances are identified structurally by a posting to an account whose `systemKind` is `"opening"`; the existing implementation demonstrates this in [accounts.ts](/work/personal/compass/apps/api/src/modules/ledger/services/accounts.ts:199), and posting shape is authoritative per [postings.ts](/work/personal/compass/apps/api/src/modules/ledger/services/postings.ts:264). As written, the service will not typecheck. The query must exclude transactions using a `NOT EXISTS` check for an accompanying posting to an account with `system_kind = 'opening'`. The proposed `transactions.userId` and `deletedAt IS NULL` predicates are otherwise correct.

- **H4/H5 are still contradicted by the acceptance criteria and test plan.** The revised design correctly exposes only raw `npsEmployeeContributionPaise` and rejects CCD(1)/CCD(1B allocation in [TASK.md](/work/personal/compass/tasks/092-scheme-limits/TASK.md:17). However, AC4 still requires both 80CCD(1) and 80CCD(1B) advisory allocations in [TASK.md](/work/personal/compass/tasks/092-scheme-limits/TASK.md:157), while P8 still calls for “NPS bucket allocation” in [TASK.md](/work/personal/compass/tasks/092-scheme-limits/TASK.md:151). The `deductionSection` rule also retains `"80CCD1B"` as a possible task-level classification. Because acceptance criteria are the repository’s source of truth, implementation could reintroduce the exact double-counting/overclaim defect the revision intended to remove. AC4 should require only `npsEmployeeContributionPaise === annualContributedPaise`, and P8 should test that the CCD eligibility fields are absent and `eligible80CPaise` is null for NPS.

- **H7’s missing-detail behavior is impossible with the specified query.** The plan requires an NPS account lacking `accountNpsDetails` to return `statusCode="data_missing"` in [TASK.md](/work/personal/compass/tasks/092-scheme-limits/TASK.md:35), but its `innerJoin` plus `tier = "tier_i"` filter in [TASK.md](/work/personal/compass/tasks/092-scheme-limits/TASK.md:131) removes such accounts from the result entirely. Load owned NPS accounts with a left join, classify a null detail as `data_missing`, include Tier I, and exclude explicit Tier II.

## Medium

- **M1 remains stale in the implementation plan.** The design and modified-files list correctly name `packages/shared/src/schemas/ledger.ts`, but P2 still instructs the implementer to update `wealth.ts` in [TASK.md](/work/personal/compass/tasks/092-scheme-limits/TASK.md:145). The required symbols do exist in the intended file: `AccountSchema`, `CreateAccountSchema`, and `UpdateAccountSchema` in [ledger.ts](/work/personal/compass/packages/shared/src/schemas/ledger.ts:183), and `toAccount()` exists in [accounts.ts](/work/personal/compass/apps/api/src/modules/ledger/services/accounts.ts:136). P2 must be corrected to prevent the field being added to the wrong contracts.

- **The NPS-detail join is not fully user-scoped.** `accountNpsDetails` has its own `userId` column in [schema.ts](/work/personal/compass/apps/api/src/modules/investments/schema.ts:48), and existing NPS services scope both `accountId` and `userId` in [account-nps.ts](/work/personal/compass/apps/api/src/modules/investments/services/account-nps.ts:36). The planned query scopes only `accounts.userId`. Add `accountNpsDetails.userId = userId` to the join condition while preserving null detail rows.

- **The revised High-severity fixes lack explicit acceptance/test coverage.** P8 omits PPF maturity-from-opening-FY, post-maturity `lifecycle_unknown`, missing `schemeOpenedDate`, Tier II exclusion, missing NPS detail, cross-user transaction exclusion, soft-deleted transaction exclusion, and opening-balance exclusion. Under the repository’s TDD workflow, these should be explicit acceptance criteria with failing tests before implementation.

## Low

- **`fyRange()` returns a tuple, but not a `[Date, Date]` tuple.** It is explicitly typed as `[string, string]` and returns inclusive ISO date strings in [financial-year.ts](/work/personal/compass/apps/api/src/lib/financial-year.ts:75). Those strings are appropriate for Drizzle `date` comparisons, but the comment in [TASK.md](/work/personal/compass/tasks/092-scheme-limits/TASK.md:112) should say `[string, string]`.

Verified as correct in the revised design: the expanded status enum; nullable `eligible80CPaise` limited to PPF/SSY; the PPF maturity example of 31 March 2026 for a June 2010 opening; all four requested paise values; and the exact NPS symbols `accountNpsDetails.accountId`, `.userId`, `.tier`, with enum value `"tier_i"` in [schema.ts](/work/personal/compass/apps/api/src/modules/investments/schema.ts:41).
