**Codex review finding: 7.6 cannot be truthful on the current data.** `cardDetails.earnRatePer100` is a single integer and `rewardEntries` is a bare point ledger. Neither knows what a point is worth or whether it was even earned, so a "best card" recommendation would compare cash discounts against points using invented values.

Model what actually decides the outcome:
- **Point value by redemption route** — the same point is worth very different amounts as cashback, air miles or catalogue goods
- **Expiry**, tracked as lots, since points expire in tranches
- **Merchant-category (MCC) exclusions** — many cards exclude fuel, rent, wallet loads, insurance and government payments outright
- **Accelerated earn caps** — the 10× that stops after ₹10,000 of spend
- **Milestone benefits** and annual-fee waiver thresholds
- **Redemption fees** and minimum redemption thresholds

`cardIssuerSettings` is issuer-level, but reward rules are usually **card-product specific** — `cardDetails.productName` and `network` already exist and should key the rules.

A deliberately constrained manual rule model is acceptable and much cheaper than exhaustive coverage. What is not acceptable is a recommendation engine that silently invents a point value.

## Acceptance criteria
- [ ] Product-level reward rules keyed by `productName`/`network`, not just issuer
- [ ] Point value per redemption route, user-configurable, with **no default that fabricates a value**
- [ ] Expiry tracked as lots; expiring points surfaced ahead of time
- [ ] MCC exclusions and accelerated-earn caps modelled and applied
- [ ] Milestone and fee-waiver thresholds tracked against actual spend
- [ ] A card with unmodelled rules is excluded from comparison rather than guessed at
- [ ] typecheck + lint + test green
