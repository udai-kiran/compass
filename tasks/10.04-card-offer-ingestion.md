Card issuers push offers constantly ("10% off on Amazon with HDFC, max ₹1,500, till 31 Aug") and they are impossible to track manually. The user forwards these to the mailbox Compass already watches; Compass extracts them into structured, expiring offers.

The whole pipeline exists — `apps/ingestor` (OAuth2 IMAP → `email_ingestions`) → `email.extract` → `apps/extractor` → reviewable rows. This adds an offer classification alongside the existing `transaction_alert` / `bill` / `card_statement` classes, plus a `card_offers` table.

Extraction must capture the terms that decide whether an offer is actually worth anything: **platform, card/issuer, discount type and rate, maximum cap, minimum spend, validity window, and whether it stacks**. The cap is what usually makes a headline "10% off" worth ₹150 rather than ₹1,500, and an offer engine that ignores caps will confidently recommend the wrong card.

Reuse the extractor's discipline exactly: redacted input, forced tool-calling gated on `ai.name !== "ollama"`, exact-name tool filtering, fail closed on 2+ matches, unparseable output never crashes, raw email retained for replay. **Offers land as reviewable rows, not as trusted truth** — a misread cap silently costs the user money.

## Acceptance criteria
- [ ] New offer classification added without disturbing existing email classes
- [ ] `card_offers` table with platform, issuer/card, discount type + rate, **max cap**, min spend, validity window, stackability
- [ ] Offers linked to the user's actual cards where the issuer matches; unmatched offers still captured
- [ ] Expired offers automatically excluded from recommendations
- [ ] Extraction reviewable before an offer is trusted; source email quoted as provenance
- [ ] Unparseable offer email degrades to nothing, never a crash
- [ ] New `ai_events` kind; table added to `ALL_TABLES`/`USER_TABLES`
- [ ] typecheck + lint + test green
