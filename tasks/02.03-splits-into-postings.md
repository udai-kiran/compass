`transaction_splits` exists to break one transaction across several categories. Under postings that is exactly what multiple `Expenses` postings with different `category_id` values already are — the table is redundant.

Fold it in and delete it. A ₹2,000 supermarket trip split ₹1,500 groceries / ₹500 household becomes one transaction with three postings: −₹2,000 bank, +₹1,500 Expenses[groceries], +₹500 Expenses[household]. It sums to zero, and the split is no longer a special case with its own table, its own service path and its own "does the split match the total?" validation — **the zero-sum invariant subsumes that check entirely**.

This also removes a latent inconsistency: today a split's amounts and its parent's `amountPaise` can disagree unless something actively validates them.

## Acceptance criteria
- [ ] `transaction_splits` removed; existing split behaviour expressed as multiple postings
- [ ] Split-vs-total validation replaced by the zero-sum invariant — no separate check
- [ ] `setSplits` equivalent works on postings, replacing the whole posting set atomically
- [ ] Category-level reporting unchanged, verified against characterization fixtures
- [ ] A split across N categories with an indivisible remainder distributes deterministically
- [ ] typecheck + lint + test green
