The bulk of the work. **32 of 65 service files reference `transactions`; nine touch `transactions.amountPaise` or `accountId` directly** and must change: `accounts`, `transactions`, `imports`, `inbox`, `cards`, `emis`, `sips`, `goals`, `user-tasks`.

Everything that creates a transaction now creates a balanced set of postings: manual entry, CSV import commit, inbox draft acceptance, recurring materialization, EMI installment posting, SIP installment recording, opening balances.

Everything that reads amounts now reads postings: balances, budgets, dashboard, trends, cashflow, forecast, net worth, insights, anomaly detection, reports, search.

Work module by module (the phase-1 boundaries exist precisely to make this bounded), and **write the characterization test before converting each consumer**. The existing 88 test files are the specification — if a converted service changes an aggregate, that is a bug, not an update to the expected value.

## Acceptance criteria
- [ ] All nine direct consumers converted; no service reads a signed amount off `transactions`
- [ ] Every transaction-creating path produces balanced postings
- [ ] Aggregates (budgets, dashboard, trends, cashflow, net worth, reports, insights, anomaly) verified against pre-conversion fixtures
- [ ] EMI principal/interest split expressed as postings without double-counting the loan-account leg
- [ ] `apps/extractor` / `apps/ingestor` still work — they write `extracted_transactions`, which only becomes postings on accept
- [ ] Backup export/restore round-trips postings correctly
- [ ] No expected value in an existing test is edited to make it pass
- [ ] typecheck + lint + test green
