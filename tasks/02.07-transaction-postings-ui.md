> **Read [`UI.md`](./UI.md) first** — stack, the components that already exist, the three-edit nav rule, and the conventions this repo enforces. Do not add a UI or charting library.

The one place the ledger conversion is visible to users. Task 2.5 keeps the simple create/update payload working, so most of `apps/web` is untouched — but reads now expose postings, and a few surfaces must show them.

**Files:** `src/routes/transactions/TransactionsPage.tsx`, `TransactionDrawer.tsx`, `QuickAdd` (in `TransactionsPage.tsx`), `src/lib/queries.ts`.

- **Transfers** — a transfer is now one transaction with two asset postings. Show the counterpart account directly instead of resolving a link; there is no `transfer_links` join any more.
- **Splits** — the split editor now edits `Expenses` postings with different categories. The "does this sum to the total?" validation is gone: the API rejects an unbalanced set, so surface that error rather than reimplementing the check client-side.
- **Drawer** — show all legs of a transaction for the multi-leg case, while a plain two-leg expense stays as visually simple as it is today.
- **QuickAdd stays exactly as it is.** Account + amount + category is still the payload; the second leg is server-side. Do not make users think in legs for an ordinary expense.

The bar is that a user recording groceries notices no difference whatsoever.

## Acceptance criteria
- [ ] Transfer rows show the counterpart account, sourced from postings
- [ ] Split editing works against postings; unbalanced sets surface the server error clearly
- [ ] Multi-leg transactions render all legs in the drawer; two-leg rows stay visually unchanged
- [ ] QuickAdd flow and keystrokes unchanged for a simple expense or income
- [ ] Types come from `@compass/shared`; no local reshaping of the posting contract
- [ ] typecheck · lint · test · `npm run build -w apps/web` all pass
