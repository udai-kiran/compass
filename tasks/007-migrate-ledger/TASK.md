### The central design decision: schema definitions do NOT physically move
Task 0.3 established the pattern "table definition lives inside `modules/<domain>/schema.ts`; `db/schema.ts` re-exports it," proven with `projection_settings` — a table with exactly one inbound dependency (`users`, itself a clean leaf) and **zero** inbound or outbound cross-references to any other still-flat table. Ledger is nothing like that:

**4 outbound FKs from ledger tables to tables that stay flat for now** (all already written with the `(): AnyPgColumn => target.id` lazy-forward-reference pattern, confirmed by direct read of `db/schema.ts`):
- `accounts.goal_id → goals.id` (planning module, task 1.5)
- `transactions.policy_id → insurance_policies.id` (protection module, task 1.4)
- `transactions.sip_id → sips.id` (investments module, task 1.3)
- `transactions.reconciled_statement_id → statement_reconciliations.id` (credit module, task 1.2)

**23 inbound FK columns across 19 still-flat tables, into the 11 ledger tables** (corrected from revision 1's imprecise "~20" — Codex's review-1 spot-check against the actual code found one omission, `emi_details.template_id → recurring_templates.id`, which revision 1's inventory had missed; exact list, confirmed against `db/schema.ts` directly): `imports.account_id`, `import_presets.account_id` → `accounts.id` (ingest, 1.7); `budget_lines.category_id`, `budget_alerts.category_id` → `categories.id` (planning, 1.5); `notification_prefs.account_id` → `accounts.id` (system, 1.8); `card_details.account_id`, `card_statements.account_id`, `bank_details.account_id`, `retirement_details.account_id`, `overdraft_details.account_id`, `reward_entries.account_id`, `statement_reconciliations.account_id` → `accounts.id` (credit/protection, 1.2/1.4); `emi_details.template_id` → `recurring_templates.id` **and** `emi_details.loan_account_id` → `accounts.id` (credit, 1.2 — both columns on the same table); `account_nps_details.account_id` → `accounts.id` (investments, 1.3); `sips.source_account_id`, `sips.target_account_id` → `accounts.id` (investments, 1.3); `insurance_policies.resource_id` → `resources.id` (protection, 1.4); `extracted_transactions.suggested_account_id`, `extracted_transactions.suggested_category_id`, `extracted_transactions.transaction_id`, `extracted_transactions.matched_transaction_id` (4 columns) → `accounts.id`/`categories.id`/`transactions.id` (ingest, 1.7); `ai_events.account_id` → `accounts.id` (AI, 1.6).

**If ledger's 11 tables physically relocated into `modules/ledger/schema.ts`** (mirroring 0.3's pattern exactly), the result is a **bidirectional circular ES-module graph** between `db/schema.ts` and `modules/ledger/schema.ts` — not the "one-directional, `export *` doesn't bind a name" issue review-2 caught in 0.3 (that was a lexical-scoping bug with a concrete fix), but a genuine cross-file cycle: `db/schema.ts` would need to import ledger tables (for the ~20 inbound FKs from still-flat tables), and `modules/ledger/schema.ts` would need to import still-flat tables (for the 4 outbound FKs). Node ESM *can* tolerate such cycles when the imported bindings are only read inside lazy closures (which `.references(() => x.id)` is) — but this is unproven at this scale in this codebase, exactly the risk category review-2 flagged for a single-table case ("Drizzle Kit failing to introspect the schema... different behavior between TypeScript checking, Node runtime, and Drizzle Kit loading"). Worse, this cycle would recur for **every one of the remaining 7 module migrations**, since nearly every domain FKs into `accounts`/`transactions`/`categories` somehow — this is not a ledger-specific problem, it's a property of the whole schema graph, and guessing wrong here means re-doing the pattern 7 more times.

**Decision: table definitions stay in `db/schema.ts`, unmoved, for this task and (by implication) for tasks 1.2-1.8.** `modules/ledger/schema.ts` becomes a **thin, named re-export** of the 11 tables **and their owned enums** from `db/schema.ts` — not a place where `pgTable(...)` calls live. **Explicit export surface (review-1 required this be concrete, not "plus any enums they use"):**
```ts
export {
  accounts, categories, resources, transactions, transactionSplits,
  transferLinks, transactionLinks, merchantRules, recurringTemplates,
  userTasks, attachments,
  accountType, categoryKind, expenseNecessity, transactionSource,
  resourceKind, recurringFrequency, recurringKind,
} from "../../db/schema.ts";
```
(The 7 enum names above are confirmed by direct read of `db/schema.ts` as the `pgEnum`s the 11 ledger tables use; implementation must re-verify this exact list against the file, not assume it's exhaustive or that no 8th enum exists.) `db/schema.ts` itself must **not** `export * from "../modules/ledger/schema.ts"` in return — that would recreate a pointless cycle (the ledger schema already re-exports from `db/schema.ts`; the barrel does not need the reverse direction, unlike task 0.3's `projection_settings` case where `db/schema.ts` genuinely needed to re-export the module's *only* copy of that table).

Services and routes inside `modules/ledger/` import table objects from this local `./schema.ts` (or `../schema.ts`), never reaching into `../../../db/schema.ts` directly for ledger-owned tables — this is the module-boundary discipline that matters; it costs nothing today and means a **future** full physical decomposition only has to change this one file, not every service/route that already imports from `./schema.ts`. This is a deliberate, documented deviation from 0.3's literal pattern (**a thin access surface, not physical ownership** — reserve "the module owns its schema" language for a file that actually contains the `pgTable()` declaration, per review-1's wording correction), made necessary by ledger's FK density — not an oversight. **Naming the future task explicitly (review-1 required this, not a vague "1.9 or later"):** `tasks/01.09-cross-module-ports.md` is amended (see Scope) to explicitly own physical schema decomposition — FK-graph/SCC analysis and relocating `pgTable()` declarations into their owning modules where an acyclic ordering exists — rather than leaving that responsibility implicit in its existing "no module imports another module's schema slice directly" acceptance criterion.

**Constraints this precedent sets for tasks 1.2-1.8 (review-1 required these be explicit, not implied):**
1. `db/schema.ts` remains the sole Drizzle Kit entry point through Phase 1.
2. Each module's thin schema.ts exports only tables/enums that module owns — never widened to re-export a foreign table for import convenience (see Mixed-table schema imports below).
3. A service/route that needs both ledger and non-ledger tables uses **split imports** (two import statements), not a widened module barrel.
4. No module's thin schema.ts is ever re-exported back through `db/schema.ts` via `export *` (only `projection_settings`-style single-owner cases, per 0.3, need that reverse direction).
5. Physical relocation is `tasks/01.09-cross-module-ports.md`'s job, named explicitly, not deferred indefinitely.
6. `CLAUDE.md` documents the distinction between physically-owned schema slices (0.3's `projection_settings`) and transitional thin access surfaces (this task's ledger tables) — see Scope.
7. Each module adds a table-identity smoke test proving its thin re-export resolves to the same object as the barrel's (see Scope/Plan).
8. Cross-module direct-table/raw-SQL access outside the moved services remains allowed during migration (documented, not fixed) and is inventoried for task 1.9 (see "Direct ledger-table access outside the moved services" below).

This also **shrinks the blast radius** of this task considerably: `services/card-due-tasks.ts` (credit module) imports `userTasks` directly from `db/schema.ts` today (bypassing the service layer) — under this design, that import needs **no change at all**, since `userTasks`'s physical home never moves. The same is true for every other file that imports a ledger table directly from `db/schema.ts` rather than through a ledger service. Only the ~15-20 files that import a ledger **service function** need their import path updated (enumerated in Scope).

### Blocking finding from review-1: single-plugin registration breaks the byte-identical snapshot — resolved by splitting the gate in two
**Corrected from revision 1:** the claim above (and revision 1's) that `printRoutes({ commonPrefix: false })` is "content-addressed by path/method, not registration order" is **wrong** — Codex reproduced this directly: collapsing the 11 interleaved registrations into one contiguous `ledgerRoutes` plugin call changes Fastify's printed tree even though no URL or method changes (first diff at the old snapshot's line 63: `/api/imports (POST, GET, HEAD)` vs. the proposed table's `/api/merchant-rules (GET, HEAD)` — the tree traversal reflects registration/plugin structure, not a sorted path list). So P5/AC1 as written in revision 1 directly contradicted each other: a real single-plugin registration cannot produce a byte-identical raw `printRoutes()` string when the 11 registrations are currently interleaved with other modules' routes.

**What the gate is actually supposed to prove** (per `tasks/README.md`: "the route-table snapshot from 0.3 proves the API surface held") is that the **set of (method, path) pairs** — the API surface — doesn't change, not that the exact tree-rendering string never changes. A pure registration-structure change (same URLs, same methods, different internal plugin nesting) is not a surface change; it's exactly the kind of change every one of the 8 Phase-1 migrations will make, since each one collapses N interleaved flat registrations into 1 module plugin.

**Fix — split the identity gate into two, both added to `apps/api/src/app.route-snapshot.test.ts`:**
1. **Canonical route-surface comparison (the new hard gate, AC1's real invariant).** Register an `onRoute` hook *before* calling `registerRoutes(app)` that records every route notification as Fastify registers routes (no text-parsing of the rendered tree — a direct, unambiguous introspection, independently verified sound by review-2 against this exact codebase: 283 notifications on the current app, fully-resolved paths, correct implicit-`HEAD` handling, and correctly observed through nested child plugins including the proposed `plugin.ts → route-file` structure). Precision requirements from review-2:
   - **Flatten and normalize methods explicitly**: `routeOptions.method` can be a string or an array; flatten to an array (`Array.isArray(m) ? m : [m]`) and uppercase each before use — do not assume every notification is a bare string.
   - **Assert no duplicate `(method, url)` pairs** before serializing (collect the full ordered list first, check for accidental duplicates, *then* dedupe/sort) — a silent `Set`-based dedup could mask an accidental double-registration.
   - **Explicit trailing-newline policy**: render as `pairs.map(p => \`${p.method} ${p.url}\`).sort().join("\n") + "\n"` (one convention, stated once, used identically for both the committed file and the live comparison — no ambiguity about a final newline).
   - Commit the result as a new `apps/api/src/route-surface.snapshot.txt`. The test compares this canonical list byte-for-byte against the committed file — this is the **actual** gate that must never change across this task (or any Phase-1 migration): if it changes, a route was genuinely added, removed, renamed, or had a method change. **Scope of this invariant (review-2's clarification):** it proves method/path identity only — not handler identity, schemas, auth/security hooks, host/version constraints, body limits, or response behavior; those remain the job of the existing behavioral tests, unaffected by this gate.
2. **Raw `printRoutes()` tree (kept as a hard regression test, but with an explicit, reviewed exception policy — corrected wording per review-2: this is not merely "informational" since the test still does a byte-for-byte assertion; what changes is the *policy* for deliberately updating it).** The existing `route-table.snapshot.txt` test stays, but its failure message is reworded to say explicitly: *"This snapshot fails on any registration-tree change. If you deliberately restructured route registration (e.g., collapsing N flat registrations into one module plugin) and confirmed the canonical route-surface snapshot is unchanged, regenerate this file and justify the diff in your task's evidence trail — do not silently accept it. If you did not intend to change registration structure, investigate before regenerating."* This task **does** legitimately restructure ledger's registration (11 calls → 1), so this raw snapshot **is expected to change** here, and the new one gets committed with the diff shown in review, cross-checked against the canonical surface staying unchanged (per P9's evidence requirements below) — unlike the canonical surface snapshot, which must not change at all.

This is a genuine, reviewed amendment to task 0.3's test infrastructure (`app.route-snapshot.test.ts`), not a reopening of task 0.3's already-shipped work — 0.3's own design was correct given what was knowable from a single trivial table with no registration-structure change; this distinction only became visible once a real multi-route migration was attempted. Both snapshot files and both test assertions ship together in this task, since this task is what needs them, and every later Phase-1 task (1.2-1.8) reuses the same canonical-surface gate unchanged.
