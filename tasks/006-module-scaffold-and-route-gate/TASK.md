## Objective
Two guards land together because Phase 1 (module migration, tasks 1.1-1.9) depends on both:

1. **Route-table identity gate**: a committed snapshot of the full route table (39 route-module registrations / ~155 URL patterns) plus a hermetic test that fails if the live table differs in any way (added, removed, renamed route, or changed method).
2. **Module scaffold**: the `modules/<domain>/` layout (`schema.ts`, `services/`, `routes/`, `plugin.ts`) and the barrel-wiring pattern that lets `db/schema.ts` become a re-export barrel without changing generated SQL — proven end-to-end by migrating `projection_settings` (the smallest available domain) into it as the **first real slice of the planning module** that task 1.5 will complete.

### Changes since review-1
1. **Circular-import fix (was High #1/#1, the single blocking issue):** `modules/planning/schema.ts` must reference `users`, but `db/schema.ts` re-exporting `modules/planning/schema.ts` while that file imports `users` back from `db/schema.ts` is a cycle. Fix: extract `users` into a new leaf file `apps/api/src/db/core-schema.ts` (no imports from `db/schema.ts` or any module) containing only the `users` table, moved verbatim. `modules/planning/schema.ts` imports `users` from `../../db/core-schema.ts` directly (a leaf, not the barrel) — no cycle. `core-schema.ts` is deliberately narrow: it holds only the shared identity table(s) that genuinely need a cycle-free home, starting with `users`. It is **not** a general destination for every cross-module foreign key — most Phase-1 cross-module references need their own explicit ownership/port decision (task 1.9's job), not an automatic move into "core."
2. **`plugin.ts` now a real Fastify plugin** (was Medium #2/#3): `modules/planning/plugin.ts` exports `planningRoutes(app)` which itself calls `app.register(projectionSettingsRoutes)`. `app.ts`'s `registerRoutes()` registers `planningRoutes`, not `projectionSettingsRoutes` directly — the plugin-entry indirection Phase 1 depends on is actually exercised, not dead code.
3. **Baseline-first ordering** (was Medium, "regressions"): the very first implementation step captures `printRoutes()` from the **unmodified, current** `app.ts` (before any file is touched) into a throwaway comparison artifact. 5. **Fixed `printRoutes()` form**: `app.printRoutes({ commonPrefix: false })` — a flat, diff-friendly representation, explicitly chosen over the default radix-tree form to reduce incidental churn on Fastify upgrades.
6. **Deterministic assertion-mechanism test replaces the manual perturbation** (was Medium, "unnecessary complexity"): rather than editing a production route and reverting it, a small pure comparison helper is unit-tested directly with synthetic before/after strings covering added, removed, renamed, and **method-changed** routes (review-1 explicitly flagged method changes, e.g. GET→POST, as untested).
