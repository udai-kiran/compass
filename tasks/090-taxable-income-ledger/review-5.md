The sanitizer correctly omits the original `.message`, `.query`, and `.params`, but preserves `.stack` at [error-logging.ts:57](/work/personal/compass/apps/api/src/lib/error-logging.ts:57). A real `DrizzleQueryError` builds its stack from the same parameter-bearing message at [errors.js:10](/work/personal/compass/node_modules/drizzle-orm/errors.js:10)–[errors.js:17](/work/personal/compass/node_modules/drizzle-orm/errors.js:17).

I constructed a real `DrizzleQueryError` containing `ABCDE1234F` and passed it through `sanitizeErrorForLog()`. The serialized sanitized output still contained:

```text
stack: Error: Failed query: insert into income_events ...
params: ABCDE1234F
```

The helper then passes that plain object directly to the request logger at [app.ts:248](/work/personal/compass/apps/api/src/app.ts:248)–[app.ts:252](/work/personal/compass/apps/api/src/app.ts:252).

The test misses the bug because its fake error uses a hand-written stack that deliberately contains only `"Failed query: ..."` and no PAN at [error-logging.test.ts:30](/work/personal/compass/apps/api/src/lib/error-logging.test.ts:30)–[error-logging.test.ts:41](/work/personal/compass/apps/api/src/lib/error-logging.test.ts:41). Some PostgreSQL constraint diagnostics can include failing-row or key details.
