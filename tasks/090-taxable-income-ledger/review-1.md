## High

### H1 — Generated `net_paise` will break backup restore unless restore metadata is updated

Drizzle 0.45.2 supports PostgreSQL stored generated columns through `generatedAlwaysAs(...)`, so normal Drizzle inserts are safe. The repository’s backup restore is not: backups use `SELECT *`, then raw `INSERT` statements. Generated columns must be stripped before restore, as already done for `transactions.search` in [restore.ts](/work/personal/compass/apps/api/src/db/restore.ts:19).

The plan only updates backup table arrays and omits `apps/api/src/db/restore.ts`. Both full and per-user restore pass through this omission map.

Required change: add `income_events: ["net_paise"]` to `OMITTED_RESTORE_COLUMNS` and corresponding restore tests—or avoid persisting `net_paise` and calculate it in the DTO/query.

There is also a domain problem: `gross - TDS` is “net after TDS,” not salary take-home. Existing payslips deliberately store gross and net independently because salary has PF, professional tax, and other deductions ([schema.ts](/work/personal/compass/apps/api/src/modules/tax/schema.ts:99)). Rename it to `afterTdsPaise` or omit it; `netPaise` is misleading for salary.

### H2 — The proposed dedup index does not prevent duplicates

The plan calls `income_events_source_idx` an ordinary index ([TASK.md](/work/personal/compass/tasks/090-taxable-income-ledger/TASK.md:51)) while AC4 says duplicates are prevented. A lookup followed by insert remains race-prone; two concurrent requests can both insert.

The extracted-transactions pattern uses a database unique index, not merely a query index ([ingest/schema.ts](/work/personal/compass/apps/api/src/modules/ingest/schema.ts:209)).

Use a partial unique index such as `(user_id, source_kind, source_id)` where `source_id IS NOT NULL`, and insert with conflict handling. Manual rows with null sources can remain non-unique.

For deposit interest, that key is still insufficient: one `deposit_details` row produces many accrual periods, and those periods are computed values without row IDs ([wealth.ts](/work/personal/compass/packages/shared/src/schemas/wealth.ts:906)). A deterministic source occurrence key—such as holding ID plus period boundaries/revision—is required.

### H3 — Automatic source population and synchronization are missing from scope

The canonical task explicitly requires dividends from `holdingEvents` and interest from the fixed-income schedule to flow automatically ([13.04-taxable-income-ledger.md](/work/personal/compass/tasks/13.04-taxable-income-ledger.md:18)). The detailed plan mentions those sources as constraints but schedules changes only inside the tax module, and its non-goals exclude automatic transaction population ([TASK.md](/work/personal/compass/tasks/090-taxable-income-ledger/TASK.md:120)).

No planned integration exists for:

- Payslip acceptance/manual creation in [payslip-review.ts](/work/personal/compass/apps/api/src/modules/tax/services/payslip-review.ts:159).
- Dividend creation and deletion in [holdings.ts](/work/personal/compass/apps/api/src/modules/investments/services/holdings.ts:255).
- Fixed-income accrual periods generated by `computeAccrualSchedule`.
- Source correction/deletion after an income event has already been accepted.

A user-invoked “derive from source” POST is not automatic flow. The plan must define reconciliation/materialization hooks or an idempotent refresh service, including what happens when a source is edited or deleted. Otherwise accepted income figures become stale.

### H4 — Provenance, source priority, override, and audit requirements are not modeled

The canonical requirements call for source priority, user override, cross-source duplicate prevention, and an audit trail explaining every included figure ([13.04-taxable-income-ledger.md](/work/personal/compass/tasks/13.04-taxable-income-ledger.md:16)). The proposed row has only `source_kind`, `source_id`, `notes`, and timestamps.

That cannot represent:

- An AIS line superseding or confirming an inferred transaction.
- Two different source rows describing the same economic income.
- Which source won and why.
- The original value before user correction.
- Who/what changed an accepted figure.
- Reversible acceptance or a replacement/supersession chain.

The routes also provide no edit/override operation despite describing the service as CRUD. Add an explicit reconciliation identity, source priority, supersedes/matches relation, and immutable change/audit history—or narrow the canonical acceptance criteria.

### H5 — The summary is not sufficient to assemble the downstream tax position

The proposed summary is not actually “per section/kind”: it hard-codes four kinds, omits section totals, and silently places `income_kind="other"` only in grand totals ([TASK.md](/work/personal/compass/tasks/090-taxable-income-ledger/TASK.md:69)).

More importantly, `salaryGrossPaise` is not taxable salary. The source payslip field is documented as monthly gross/CTC, while exemptions and deductions live in components. Feeding this directly into 13.10 would materially overstate taxable income. Advance tax requires taxable amounts after applicable salary treatment and deductions, plus assumptions and timing; its acceptance criteria explicitly require a liability assembled from salary, gains, interest, rent, and TDS ([13.10-advance-tax.md](/work/personal/compass/tasks/13.10-advance-tax.md:24)).

At minimum, expose:

- Reconciled totals by income kind and section.
- `otherGrossPaise`/`otherTdsPaise`, or a dynamic exhaustive breakdown.
- A clearly named `taxableAmountPaise` distinct from cash gross/net.
- Accepted event counts and completeness/estimate indicators.
- Period/date breakdown usable by downstream calculations.
- Capital gains kept separate and joined explicitly by 13.10/13.11.

## Medium

### M1 — The state-machine shape matches, but the verification plan is incomplete

`pending → accepted | rejected` using `UPDATE ... WHERE user_id=? AND id=? AND status='pending' RETURNING` matches the core extracted-transactions pattern ([review-actions.ts](/work/personal/compass/apps/api/src/modules/ingest/services/review-actions.ts:56)). The plan should also require tests for:

- Two concurrent accept/reject attempts: exactly one succeeds and the other returns 409.
- Missing or cross-user IDs returning 404 without revealing existence.
- `accepted_at` set only for accepted rows.
- Rejected rows retaining `accepted_at = NULL`.
- Any corrections and source materialization occurring in the same transaction as acceptance.
- Responses based on the claimed `RETURNING` row when future transitions/restore are supported.

The current P8 only says “state machine” and does not capture these concurrency and ownership invariants.

### M2 — Database constraints are too weak for financial and lifecycle invariants

All discriminator columns are unrestricted text, and no checks enforce:

- `gross_paise >= 0`.
- `tds_paise >= 0`.
- `tds_paise <= gross_paise`.
- Valid status/source/income-kind values.
- `accepted_at IS NOT NULL` exactly when accepted.
- `source_id IS NULL` only for manual sources and non-null for derived sources.

Shared Zod validation alone does not protect migrations, restore, or internal service writes. Use pg enums or check constraints and add invariant tests.

### M3 — `fy` can disagree with `accrual_date`

The table stores both values but the plan does not require `fy === fyOf(accrual_date)`. The repository already has strict FY helpers ([financial-year.ts](/work/personal/compass/apps/api/src/lib/financial-year.ts:23)), and the payslip contract validates that its month belongs to the supplied FY.

Validate this in the shared create schema and service, ideally deriving FY server-side from the accrual date. Otherwise the same event can be listed and aggregated under the wrong year.

### M4 — `source_id` is not an FK, and source ownership is underspecified

The table comment calls `source_id` an FK, but a single polymorphic UUID cannot have foreign keys to payslips, holding events, transactions, and future AIS rows. The plan must call it a logical reference or use typed nullable FK columns/a source-link table.

Every derivation must load the source through the authenticated user’s ownership chain. `holding_events` has no `user_id`; ownership is through `holding_id → holdings.user_id` ([investments/schema.ts](/work/personal/compass/apps/api/src/modules/investments/schema.ts:126)). Tests should prove cross-user source UUIDs cannot be derived or inspected.

### M5 — The proposed fields lose information needed for reconciliation

`payer_pan_tan` merges identifiers with different formats and meanings, making validation and AIS/Form 16 matching ambiguous. Likewise, `"manual"` is listed as a tax section even though it is a source kind, not a section.

Use separate identifier type/value fields, or separate PAN/TAN columns. Make section nullable or use a distinct “not applicable/unknown” value. The canonical task also asks for an accrual period and links to transaction, holding, account, or payslip; the proposal has only one date and one opaque source UUID ([13.04-taxable-income-ledger.md](/work/personal/compass/tasks/13.04-taxable-income-ledger.md:14)).

## Low

### L1 — The claimed downstream dependency on 13.7 and 13.11 is inaccurate

Task 13.7 does not depend on 13.4 in its frontmatter and consumes deduction sources such as EPF components and tax-saver investments, not taxable-income summary fields ([13.07-80c-80d-basket.md](/work/personal/compass/tasks/13.07-80c-80d-basket.md:7)). Task 13.11 models capital-loss set-off and similarly needs capital-gains/loss data rather than the proposed income summary ([13.11-loss-carryforward.md](/work/personal/compass/tasks/13.11-loss-carryforward.md:20)).

13.10 and 13.13 are the direct consumers. The plan should avoid designing the summary around nonexistent 13.7/13.11 requirements.

### L2 — Route paths must be relative inside the tax plugin

The tax module is registered with the `/api/tax` prefix, and existing route files declare relative paths ([plugin.ts](/work/personal/compass/apps/api/src/modules/tax/plugin.ts:2), [app.ts](/work/personal/compass/apps/api/src/app.ts:155)). The plan lists full `/api/tax/income-events` paths. Implementation must register `/income-events`, `/income-events/:id`, etc., or it risks producing `/api/tax/api/tax/...`.

Register `/income-events/summary` before the parameterized `/:id` route for consistency with the repository’s static-before-parameterized convention.

### L3 — Plaintext PAN/TAN storage is expected, but privacy controls should be explicit

Plaintext structured identifiers are consistent with the current local data model; for example, PRAN is stored as text in the investments schema ([investments/schema.ts](/work/personal/compass/apps/api/src/modules/investments/schema.ts:44)). There is no repository rule requiring field-level encryption for PAN/TAN. Full and portable backups are encrypted, although the authenticated JSON data export is intentionally plaintext.

The plan should nevertheless require:

- PAN/TAN validation and normalization.
- No raw identifier in logs, errors, analytics, or AI event payloads.
- Redaction before any external AI request, matching existing PAN redaction behavior.
- Authorization-scoped responses and source lookups.
- Explicit treatment of `payer_pan_tan` as sensitive data.

Plaintext-at-rest itself is not a blocker for this task.
