Closes Phase 1. Replace the remaining raw cross-domain reads with declared interfaces, so a module depends on a contract rather than another module's tables.

Primary case: net worth reaching into ledger, credit, investments and protection to classify balances into buckets — becomes a `NetWorthContributor` port each module implements. Same treatment for the reward earn-rate lookup (1.2) and goal projections (1.5), both of which the shopping pillar consumes later.

Also: delete the emptied flat `services/` and `repositories/` folders. `repositories/` has only held `users.ts` and has been a fiction for a long time — either fold it into the system module or drop it, but do not leave a folder implying a layer that does not exist. As part of that flat-services cleanup, `services/autopilot.ts` (surfaced by task 1.5, `tasks/014-migrate-planning/`) needs a home: it depends on three planning services (`cashflow`, `goal-plan`, `goals`) but is routed nowhere and is driven only by the weekly `autopilot.goals` cron in `jobs/index.ts` — decide whether it belongs in the planning module or an automation module rather than leaving it flat. Note: task 1.6 (`tasks/016-migrate-automation/`) already created `modules/automation/` and moved `services/ai-settings.ts` into it, so `automation` is a real, existing home for `autopilot.ts` should 1.9 choose it.

This task also owns physical schema decomposition — the piece task 1.1 (`tasks/007-migrate-ledger/`) explicitly deferred rather than guessed at. Task 1.1 established `modules/ledger/schema.ts` as a thin, named re-export of the ledger tables (still physically defined in `db/schema.ts`), not a physical relocation, because ledger's FK density (4 outbound FKs to still-flat tables, 23 inbound FK columns from still-flat tables) made a naive per-module physical split risk a genuine bidirectional ES-module cycle — a risk that recurs for every one of tasks 1.2-1.8, since nearly every domain FKs into accounts/transactions/categories somehow. Every one of tasks 1.1-1.8 is expected to introduce the same kind of transitional thin-schema surface for at least some of its tables, and this task is where that gets resolved for good, not left indefinitely. Concretely, this task owns:
- Producing the full cross-module foreign-key graph (every table, every FK edge, across all 8 migrated modules) and its strongly-connected-component (SCC) decomposition.
- Assigning every physical `pgTable()` definition to a final owning module wherever the graph is acyclic for that table.
- An explicit policy for tables that remain in a cyclic SCC after that assignment — e.g. a small shared "core" schema file per SCC, following the `db/core-schema.ts` precedent from task 0.3, rather than leaving them in a monolithic `db/schema.ts` indefinitely.
- Converting or removing every transitional thin-schema surface introduced by tasks 1.1-1.8 (`modules/ledger/schema.ts` included) — by the end of this task, a module's `schema.ts` holds the real `pgTable()`/`pgEnum()` definitions it owns, not a re-export of tables still physically defined elsewhere.
- Retaining exactly one Drizzle Kit entry point throughout (same constraint tasks 0.3 and 1.1 held to).
- Proving zero migration diff and table-object identity for every relocation, using the same content-hash-manifest (`apps/api/drizzle/`) and `schema.smoke.test.ts`-style object-identity techniques established in tasks 0.3 and 1.1.
