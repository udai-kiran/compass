The payoff for the income ledger, and the piece of `PRD-wow-features.md` #2 that survives intact: **reconcile what the tax department already believes about you against what Compass knows.**

Import AIS/26AS (and Form 16) and match line by line against the 11.4 income events — interest the bank reported but you never recorded, dividends missing from your ledger, TDS credited under a PAN you forgot, a high-value transaction flagged in AIS.

Reuse the staged, reviewable import pattern from `services/imports.ts` and the matching approach from `statementReconciliations`: **staged, reviewable, reversible — never auto-applied.** Tax documents disagreeing with your ledger is normal and usually means *your ledger* is incomplete; the discrepancy is the product.

Given these documents contain PAN and full income detail, they are the most sensitive artifacts Compass will handle. Redaction before any model call and no raw logging are non-negotiable.

## Acceptance criteria
- [ ] AIS/26AS and Form 16 imported through the staged, reversible import path
- [ ] Line-by-line matching against income events, with unmatched items on both sides surfaced
- [ ] Discrepancies presented as reviewable items, never auto-applied to the ledger
- [ ] TDS credits reconciled against recorded deductions
- [ ] PAN and income detail redacted before any model call; never logged raw
- [ ] Documents stored via the `Storage` abstraction
- [ ] Works with partial documents — a missing section does not fail the import
- [ ] typecheck + lint + test green

## Implementation notes (post-review pass)

Fixes from the independent review:

- **TDS in match semantics** — a line only `matched` when gross AND TDS both
  equal the event; equal-gross/different-TDS is now an `amount_mismatch`.
  The ledger side of the report is surfaced too: `unmatchedLedgerCount`
  counts this FY's events no reported line accounted for.
- **Accept is atomic** — the pending→accepted flip and all verdict/counter
  writes happen in ONE transaction under a row lock, so an accepted statement
  can never be stale.
- **Storage lifecycle lives in the service** — attach uploads first and
  compensates (deletes the new object) if the row update fails; replacing a
  document deletes the superseded key only after the row points at the new
  one; deleting a statement removes its stored document.
- **No raw filenames** — `sourceLabel` records a content-type description
  ("PDF upload"), never the uploaded filename. A reported "TAN" that is
  PAN-shaped is used for matching but masked out of API echoes (`panLast4`
  on the statement header remains the identity confirmation).

Deliberate deferral, recorded: deterministic parsing of REAL AIS/TRACES/Form-16
export formats (upload → auto-populated lines) needs genuine fixtures of those
exports to parse against; guessing at their shapes would produce silently wrong
imports of exactly the documents this feature exists for. v1 therefore takes
typed/pasted lines through the same staged path and retains the raw document
via Storage; structured-export parsing lands when real fixtures are available.

## Implementation notes (round-2 review pass)

- **Global exact-first matching** — the greedy matcher could steal an event a
  LATER line matched exactly, turning both into mismatches. `matchStatementLines`
  now runs two passes: every line claims its first unconsumed qualifying event
  with identical gross AND TDS; only then do leftover lines pair with leftover
  qualifying events as `amount_mismatch`. Regression test pins the steal case;
  proven to bite (fails against the old greedy body).
- **Compare-and-swap document replace** — the attach update matches on the
  observed `document_key` (`IS NULL` when none); a concurrent replacement loses,
  deletes its freshly uploaded object, and surfaces 409 instead of orphaning the
  winner's object.
- **Matcher docstring aligned with reality** — an absent section on EITHER side
  acts as a wildcard (lenient both ways was always the code's behaviour; only
  the comment claimed otherwise).
- **UI** — the inverse-mismatch chip reads "ledger only" (events no reported
  line accounted for), not "not in ledger"; pending statements now render Delete
  alongside Accept/Reject so they can be discarded without a state transition.

## Implementation notes (round-2/3 review passes)

Fixes from independent review:

- **PAN masked at WRITE time** — `createTaxStatement()` previously stored a
  PAN-shaped `payerTan` verbatim (only API echoes were masked). The insert now
  runs `maskPayerTan()` first, so a full PAN never sits in Postgres. Matching
  stays sound: the matcher falls back to normalised payer-name equality when
  TAN is absent on either side, and an anonymous line correctly does not
  force-match.
- **Ledger-only discrepancies surfaced as reviewable rows** — task criterion
  "unmatched items on both sides" was only met by an integer count. Detail
  responses now carry `unmatchedLedgerEvents` (kind, payer, gross, TDS,
  accrual date) via the pure `deriveUnmatchedLedgerEvents()`, rendered in the
  UI under "Recorded in your ledger but not in this statement".
- **Detail count always agrees with its list** — `unmatchedLedgerCount` on the
  DETAIL response is now derived live (`unmatchedLedgerEvents.length`) instead
  of read from the reconcile-time column; a never-reconciled statement can no
  longer show count 0 beside a full list. The LIST endpoint keeps the persisted
  counter (deriving live would mean an N+1).
- **TDS > gross rejected at validation** — `CreateTaxStatementLineSchema` gained
  the same `.refine(tdsPaise <= grossPaise)` the income-event schema already
  had; previously such submissions reached the DB CHECK and surfaced as an
  untranslated 500 instead of a clean 400.
