> **Read [`UI.md`](./UI.md) first** — stack, the components that already exist, the three-edit nav rule, and the conventions this repo enforces. Do not add a UI or charting library.

The highest-stakes UI in the release: **a user must never be uncertain whether something is visible to their household.** Ambiguity here reads as a privacy bug even when the backend is correct.

**Files:** a shared `src/components/SharingControl.tsx`, wired into `src/routes/settings/AccountDetailPage.tsx`, `src/routes/goals/GoalsPage.tsx`, `src/routes/budgets/BudgetsPage.tsx` and the transaction drawer.

- **Private is the default and must look like it.** Current visibility is always stated explicitly — never inferred from an unchecked box the user has to interpret.
- Sharing is an **explicit grant**, never implied by household membership; the control says who gains access, by name.
- Un-sharing states what will be lost and to whom.
- Where a record has shared children (a shared account's transactions), say so — users consistently underestimate what a share includes, and this is where a real privacy surprise would come from.

## Acceptance criteria
- [ ] One reusable control, used identically everywhere — no per-page variants
- [ ] Current visibility always explicit; private state visually distinct from shared
- [ ] Share/un-share names the people affected
- [ ] Cascading effect on child records stated before confirming
- [ ] Control absent (not disabled-and-confusing) when the user has no household
- [ ] Keyboard accessible with a clear focus state
- [ ] typecheck · lint · test · `npm run build -w apps/web` all pass
