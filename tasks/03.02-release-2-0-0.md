Cut the release. **2.0.0 is a foundation release**: the module migration, the domain event bus and the double-entry ledger. It is deliberately near-invisible to users — the pillars built on it ship from 2.1.0 onward.

**The production database is recreated from scratch for this release.** That is what makes the double-entry conversion tractable, and it must be stated plainly in the release notes: there is no upgrade path from 1.x data. Anyone with data to keep should export it first via the existing JSON export, and re-import through the CSV/statement pipeline afterwards.

Versioning is derived from git tags at build time (`git describe` in `publish.yml`) — root `package.json` stays `0.1.0` and is not part of the flow. Tagging is the whole mechanism:

```bash
git tag v2.0.0 && git push --tags
```

CI then publishes `2.0.0`, `2.0`, `latest` and `sha-<full>` for api, web, ingestor and extractor to GHCR. Operators bump `COMPASS_VERSION` on the host and run `make update` (host-side, not in this repo).

Ship continuously through 1.9x as phases land; 2.0.0 is a marker cut at the end, not a long-lived release branch. At roughly five releases a day, a frozen branch would fight how this project actually works.

**Pre-tag verification** is the full end-to-end pass: migrations applied as the `compass` role, app boots with AI fully disabled, a plain `docker compose up` still does not start `ingestor`/`extractor`, and the shopping and household flows walked by hand.

**Commit hygiene:** stage files explicitly — a private statement PDF and `apps/docs/.docusaurus/` sit in the working tree. Never `git add -A`.
