## Objective
Delete the stringly-typed `onResponse` hook in `apps/api/src/app.ts` (currently lines 195-203) that pattern-matches `req.url` against `/^\/api\/(transactions|transfers|imports|recurring|inbox)/` to decide whether to invalidate the per-user cache and enqueue a debounced budget evaluation. Replace it with the `ledger.mutated` domain event (from task 0.1's `EventBus`, already merged): every code path in these five route families (plus the recurring background job and boot-catchup) that actually changes ledger-derived state emits `ledger.mutated({ userId })`, and exactly one subscriber (wired once in `app.ts`) reacts by calling `invalidateUserCache` + `enqueueBudgetEvaluation`. Renaming a route or adding an unrelated mutating endpoint under one of the five URL prefixes must no longer silently change behaviour; conversely, a real ledger mutation in one of these families must not depend on which URL prefix it happens to sit under. This task does not claim universal coverage of every ledger-writing code path in the app — see the pre-existing-gap note below and Non-Goals.

Corresponds to GitHub issue #134 (`tasks/00.02-retire-url-regex-hook.md`, roadmap id `0.2`, depends on `0.1` — merged in PR #154).

**Codex review-1 findings folded into this revision** (see `review-1.md`): recurring-template deletion must stay an invalidation trigger (High #1 — `getForecast()`'s `cached()` wrapper reads `recurringTemplates` directly, confirmed at `services/cashflow.ts:55,83`); AC2/T5 were overclaiming "exactly one call site" when `budgets.ts`/`sips.ts`/`emis.ts` keep their own direct calls unchanged (High #2); the plan must not claim this covers *every* ledger-mutating path in the app — `recordEpfContribution()` (`POST /api/epf-contributions`) and `logPremium()` (`services/insurance.ts:322`) also call `createTransaction()` outside the five migrated route families, a **pre-existing gap** (neither was ever matched by the old regex either, so this task neither creates nor fixes it — Medium #3); `EventBus.emit()` is fire-and-forget via `queueMicrotask` (`event-bus.ts:66-93`), so cache invalidation is no longer awaited before the HTTP response returns — an accepted, explicit behavior change vs. today's awaited hook (Medium #4); tests must account for that asynchrony rather than asserting immediately after emit (Medium #4); P8's original "arbitrary URL route" test design didn't prove production wiring correctness and has been replaced (Medium #5).

## Root Cause
Not a bug fix — a designed-in-advance refactor. Confirmed by reading the code (not assumption):
- `app.ts:197-203` today: `if (req.method === "GET" || reply.statusCode >= 400 || !req.session) return; if (/^\/api\/(transactions|transfers|imports|recurring|inbox)/.test(req.url)) { invalidateUserCache(...); enqueueBudgetEvaluation(...); }`.
- `invalidateUserCache` (`services/cache.ts`) is a single Redis `INCR cachever:<userId>` — cheap, idempotent, safe to over-call; the only real risk is under-calling it (stale `dashboard`/`cashflow`/`insights` reads, the only three call sites of `cached()` in the codebase — confirmed by grep).
- `enqueueBudgetEvaluation` (`jobs/index.ts`) already does its own debouncing (`jobId: eval-${userId}-...`, 5s delay) — untouched by this task.
- The hook is not the only call site: `routes/recurring.ts`'s `materializeNow` helper and `jobs/index.ts`'s `recurring.materialize`/boot-catchup paths **already** call `invalidateUserCache`/`enqueueBudgetEvaluation` directly, because `materializeDue()` can affect *other* users' caches, not just the requesting session's — the URL-keyed hook structurally cannot do that. This is direct evidence the replacement must work from an explicit `userId`, not a request.

**Design decision (services vs. routes as emitters):** `tasks/00.02-retire-url-regex-hook.md` says "the services that actually mutate the ledger emit it." Services in this codebase take `(db: Db | Tx, userId, ...)` only — no Fastify instance, no event bus reference — and none of the five affected service files (`services/transactions.ts`, `transfers.ts`, `imports.ts`, `recurring.ts`, `inbox.ts`) currently take any side-effect dependency beyond the DB handle. Threading `EventBus` through every mutating service function's signature is a materially larger, invasive change than task 0.1 or the rest of phase 0 and isn't required to satisfy any acceptance criterion literally. Instead, **the outermost caller that authoritatively knows the `userId` emits**: the route handler for HTTP-triggered mutations, and `jobs/index.ts`'s worker/boot code for the background-triggered recurring-materialize path (which has no HTTP request at all). This satisfies every AC (below) without a service-layer signature change. Flagging this explicitly for Codex plan review since it's a deviation from the task file's literal wording.

**Narrowing decision (scope of what emits):** the old regex fires on *any* non-GET request under the five prefixes, including several that never touch a ledger-relevant table:
- `imports.ts`: `POST /api/imports` (staging upload), `PUT .../mapping`, `PATCH .../rows/:rowId`, `DELETE /api/imports/:id` (only legal on a non-committed batch, per `deleteImport`'s own guard) — none touch the `transactions` table. Only `POST .../commit` and `POST .../rollback` do.
- `inbox.ts`: `POST /api/inbox/:id/reject`, `.../restore`, `.../unmatch` only touch `extracted_transactions`, confirmed by reading `services/inbox.ts` (`restoreOrphan`, `rejectExtracted`, `unmatchDuplicate` — no write to `transactions`). Only `.../accept`, `.../repayment`, and `POST /api/inbox/transfer` create ledger transactions.
- These two feed no cached read (only `dashboard.ts`, `cashflow.ts`, `routes/insights.ts` call `cached()`, and none read import-staging or inbox-draft rows).

**Correction from review-1:** `recurring.ts`'s `DELETE /api/recurring/:id` (`deleteTemplate`) was originally proposed for the same narrowing — it only deletes the template row, never touches materialized transactions. That's true, but irrelevant: `services/cashflow.ts:55` wraps `getForecast()` in `cached()`, and `cashflow.ts:83` reads `recurringTemplates` directly to project future obligations. Deleting a template changes `getForecast()`'s output, so **`DELETE /api/recurring/:id` must still emit** — corrected in Scope/Plan below. The event's practical meaning is therefore "ledger-derived cached views may have changed," not strictly "a transaction row was written" — recurring create/update-with-no-materialization already relied on this broader meaning via the existing `materializeNow` fallback branch, and delete now matches it for consistency. Not worth a second event type for one extra call site.

This task still **narrows** cache-invalidation triggers versus today's blanket "any non-GET request under the prefix," but only where confirmed safe against the three actual `cached()` consumers (imports staging, inbox reject/restore/unmatch) — a deliberate, in-scope behaviour change (fewer redundant `INCR`s), not a regression.

## Plan
- P1: Delete the `onResponse` hook in `app.ts`; extract `registerLedgerCacheSubscriber(app)` and call it right after `app.decorate("eventBus", eventBus)`, **before** `await startJobs(app)` (registration must precede boot-catchup's emits, or they're lost — corrected from review-1's original "order doesn't matter" claim)
- P2: Add `app.eventBus.emit("ledger.mutated", { userId: req.session!.userId })` to the five `transactions.ts` mutating handlers, after the service call succeeds — store the awaited result in a local, emit, then return/send it (handlers currently written as `reply.code(201).send(await createTransaction(...))` need restructuring to await-then-emit-then-send). Success only, never on a thrown error; a `bulkAction` result with zero affected rows still emits (harmless over-invalidation, same as today's semantics)
- P3: Same for the three `transfers.ts` mutating handlers
- P4: Same for `imports.ts`'s `commit` and `rollback` handlers only — emit after the awaited result, never before/inside the service's own DB transaction (so a later rollback of the *service's* internal transaction can't leave an emitted event for a write that didn't happen)
- P5: Same for `inbox.ts`'s `accept`, `repayment`, and `transfer` handlers only
- P6: Convert `recurring.ts`'s `materializeNow` to emit per-`uid` (from `res.userIds`) instead of calling `invalidateUserCache`/`enqueueBudgetEvaluation` directly, including the `else` branch. Add an emit to the `DELETE /api/recurring/:id` handler too (corrected — template deletion changes `getForecast()`'s cached output; see Root Cause)
- P7: Convert `jobs/index.ts`'s two direct-call sites (`recurring.materialize` handler, boot-catchup) to emit per-`userId` from `res.userIds`/`boot.userIds`
- P8: Test coverage, redesigned twice per review-1 and review-2 (the original "arbitrary URL route" harness proved a hand-rolled duplicate, not production wiring; the first redesign's "minimal fake app object" wouldn't type-check against `registerLedgerCacheSubscriber(app: FastifyInstance)` and tested only half the subscriber's contract):
  - P8a: unit-test the exported `registerLedgerCacheSubscriber` against a **real, minimally-decorated Fastify instance** (`Fastify({ logger: false })`, no unsafe casts, no narrowed/duck-typed param type) — decorate real `redis` (`createRedis(config.REDIS_URL)`), a real BullMQ `Queue("alerts", { connection })` for `app.queues.alerts` (same construction `jobs/index.ts` already uses), and a real `EventBus`. Call `registerLedgerCacheSubscriber(app)`, then `app.eventBus.emit("ledger.mutated", { userId })`, then **await a completion signal** before asserting — bounded-poll `cachever:<userId>` in Redis for a change from its recorded baseline (never assert immediately after `emit()`; it returns before the `queueMicrotask`-dispatched subscriber runs). Assert **both** subscriber effects: (a) `cachever:<userId>` incremented, and (b) the alerts queue actually received the debounced job — compute the expected `jobId` (`eval-${userId}-${Math.floor(Date.now()/5000)}`) and confirm it via `queue.getJob(jobId)` (or an equivalent BullMQ query), not just that no error was thrown
  - P8b: a route-injection test (the `user-tasks.route.test.ts` `buildTestApp` pattern — real Postgres/Redis, `setupAuth`/`setupSecurity`, no `startJobs`) that decorates a real `EventBus` and registers `transactionRoutes` — **does not** need `registerLedgerCacheSubscriber` or BullMQ here, since this test's job is only to prove the route itself emits, not that the subscriber reacts correctly (P8a already proves that in isolation). Add a test-only observer via the real `EventBus.on()` API (no cast/spy-object needed — `.on()` is real, public API) that records `{event, payload}` pairs, `POST /api/transactions`, and bounded-poll the observer's recorded list for a `ledger.mutated` entry with the expected `userId` (again: fire-and-forget, so poll, don't assert immediately)
  - P8c: a negative case using the same `.on()` observer — a request that 400s (e.g. malformed body) must produce **no** `ledger.mutated` entry after the same bounded quiet period (long enough to rule out "not yet delivered" rather than "never emitted") — this is the deterministic, non-Redis-dependent version of the negative proof; assert it in addition to (not instead of) confirming `cachever:<userId>` is unchanged
  - P8d: source-level check (part of Verification, not necessarily a `node:test`) that the regex/`onResponse` hook is gone from `app.ts`

**Accepted behavior change (review-1 Medium #4, corrected per review-2):** the deleted hook awaited `invalidateUserCache`/`enqueueBudgetEvaluation` before the HTTP response returned; `EventBus.emit()` is synchronous-return + `queueMicrotask`-dispatched (already true of task 0.1's merged implementation), so after this task a mutating request (or the recurring worker/boot-catchup path) can complete before its cache invalidation/budget-eval enqueue has finished. Failures remain isolated and logged (a subscriber throw/reject is caught by `EventBus` itself, and `enqueueBudgetEvaluation` already try/catches its own queue errors), **but they no longer propagate to or delay the originating request/job** — a real, accepted reduction in completion guarantees versus today's awaited hook, not a claim that "nothing weakens." Documented here, not hidden.

## Acceptance Criteria
- AC1: The regex hook is deleted from `app.ts` (no `/^\/api\/(transactions|...)/ test(req.url)` anywhere in the codebase)
- AC2: `invalidateUserCache` and `enqueueBudgetEvaluation` are called from exactly one place — `registerLedgerCacheSubscriber`'s subscriber in `app.ts` — for `transactions.ts`, `transfers.ts`, `imports.ts`, `inbox.ts`, `recurring.ts` (route), and `jobs/index.ts`'s recurring-materialize/boot-catchup paths; no direct calls to either function remain in those six files. `routes/budgets.ts`, `routes/sips.ts`, and `routes/emis.ts` keep their existing direct calls **unchanged** — explicitly out of scope (Non-Goals), not a contradiction of "exactly one place" within the migrated set
- AC3: Every path in the migrated set emits `ledger.mutated`: the 5 transactions handlers, the 3 transfers handlers, imports commit/rollback, inbox accept/repayment/transfer, `recurring.ts`'s `materializeNow` (both branches) plus its `DELETE /api/recurring/:id`, and both job-layer recurring-materialize paths (worker handler and boot-catchup)
- AC4: Budget-eval debouncing (`jobId: eval-${userId}-...`, 5s delay) is preserved unchanged — `enqueueBudgetEvaluation`'s own implementation is untouched
- AC5: A test proves cache invalidation is driven by the emitted event, not URL matching — the extracted subscriber verified in isolation against both of its effects (P8a: cache invalidation *and* budget-eval enqueue), a real route proven to emit end-to-end (P8b), and a negative case showing a failed request emits nothing (P8c)
- AC6: `npm run typecheck`, `npm run lint`, `npm run test -w apps/api` all pass with zero new failures
- AC7: The fire-and-forget behavior change (emit is no longer awaited before the response returns) is accepted and documented, not silently introduced — reviewed by Codex against the current `EventBus.emit()` implementation

- Not changing `enqueueBudgetEvaluation`'s debounce implementation
- Not threading `EventBus` through `services/*.ts` function signatures (see Root Cause design decision)
