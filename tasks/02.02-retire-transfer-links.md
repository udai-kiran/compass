**The clearest payoff of the conversion, and a net deletion.**

Today a transfer is two transactions stitched together by a `transfer_links` row, and every aggregate in the app must then exclude them — via a correlated `EXISTS` subquery (`services/transactions.ts:38-40`) referenced in **25 places across the services layer**.

Under postings a transfer is simply one transaction with two asset-account postings. There is nothing to link and nothing to exclude: income and expense aggregates read the `Income` and `Expenses` system accounts, and a bank-to-bank movement never touches either.

Delete `transfer_links`, the `isTransferSql` fragment, and every exclusion call-site.

**Keep transfer *detection*** — matching two imported rows that are really one movement is still genuinely useful during CSV import. What changes is that detection now produces one balanced transaction instead of two rows plus a link.

## Acceptance criteria
- [ ] `transfer_links` table and `isTransferSql` removed
- [ ] All 25 exclusion call-sites removed; aggregates read the system accounts instead
- [ ] A transfer is one transaction with two asset postings; the counterpart account is visible without a join to a link table
- [ ] Import-time transfer detection retained, now producing a single balanced transaction
- [ ] Income/expense/spend aggregates verified unchanged against fixtures (characterization tests written **before** the change, per TDD.md)
- [ ] Deleting a transfer removes both legs atomically — impossible to orphan one
- [ ] typecheck + lint + test green
