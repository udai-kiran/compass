Today `buildGoalPlan()` sets `allocationDrifted: boolean` when current equity strays past `DRIFT_BAND_PCT` (10) of target, or when a goal that should be invested sits over `OTHER_BAND_PCT` (50) in cash/gold. **A boolean is a notification, not a plan** — it tells the user something is wrong and leaves them to work out what to do.

Turn it into instructions with amounts: which leg is overweight, by how much in rupees, and the switch that corrects it. Two correction routes, and the cheaper one is usually not the obvious one:
- **Redirect new contributions** — fix drift with future SIP flow, no sale, no tax event. Prefer this whenever it closes the gap in reasonable time.
- **Switch existing corpus** — only when drift is too large for contributions to correct.

Also produce the **near-goal de-risking schedule**: as the target date approaches, the glide path (4.1) implies a planned sequence of shifts into debt. Surface those as dated, upcoming actions rather than as a surprise drift alert a month before the goal matures.

## Acceptance criteria
- [ ] Drift reported as specific amounts per leg, not a boolean
- [ ] Contribution-redirection offered first; corpus switching only when redirection is insufficient
- [ ] Near-goal de-risking surfaced as a dated schedule derived from the 4.1 glide path
- [ ] Existing drift bands (`DRIFT_BAND_PCT`, `OTHER_BAND_PCT`) reused, not redefined
- [ ] Respects the "other" bucket semantics — cash in an emergency fund is never flagged
- [ ] Advisory only: nothing is auto-executed, no order is ever placed
- [ ] Deterministic, integer paise, unit-tested
- [ ] typecheck + lint + test green
