## Objective
Replace single-entry (`transactions.accountId`+`amountPaise`; balance = `accounts.openingBalancePaise + sum(amountPaise)`) with double-entry postings: a `postings` table carries the money, `transactions` becomes a header, every transaction's postings sum to exactly zero, and an account's balance is purely `sum(postings)`. System accounts (`Expenses`, `Income`, `Opening Balances`) are seeded per user. Category + necessity move onto the posting. Integer paise throughout, provably.

Roadmap: `tasks/02.01-postings-model.md`. Depends on 1.9 (done, v2.1.0). Blocks 2.2–2.7.

## Governing constraint (root cause of the sequencing)
1. **Zero-sum per transaction** forces the transfer/split remodel: a transfer becomes ONE transaction with two non-system-account postings (not two independently-balanced rows); a split becomes multiple `Expenses` postings on one transaction. This is the functional remodel the roadmap filed under 2.2/2.3.
2. **No dual-write / no backfill** (prod DB recreated from scratch). Removing the header money columns breaks ~45 ORM compile sites + every raw-SQL aggregation at once (`investigation-1.md` §3). Write path, read/aggregation path, column removal, backup, and shared contract must land in ONE atomic changeset.

## Resolved design decisions (from review-1)
- **D1 Transfer identity.** Remodel transfers in 2.1 as ONE transaction with two non-system-account postings. Change the transfer DTO (`CreateTransfer`/`TransferResult`) and the transfer-aware web consumers (`TransactionsPage.tsx`, `AccountLedgerPage.tsx`). NO synthetic two-leg projection. Retire/rewrite `linkTransfer`/`autoLinkTransfers`/`unlinkTransfer`/`suggestTransfers`.
- **D2 Ordinary-txn DTO projection (keeps web mostly untouched for non-transfers).** `hydrate()` reconstructs the legacy `Transaction` DTO: `accountId`/`amountPaise` ← the single non-system posting; `categoryId`/`necessity` ← the system counter-posting; `splits` ← the N `Expenses` postings with **amounts negated** to legacy signed semantics and `note` from the posting. Opening transactions recognized by their `Opening Balances` posting.
- **D3 Split note.** Add `note text NOT NULL DEFAULT ''` to `postings` for lossless split reconstruction.
- **D4 Liability-inflow semantics (parity-critical).** Income/expense reporting MUST preserve today's rule: negative real-posting = expense; positive real-posting = income ONLY when the real account is non-liability (`LIABILITY_ACCOUNT_TYPES`); opening + transfer transactions excluded. Implement by aggregating postings on REAL (non-system) accounts joined to `accounts.type`, excluding transfer-shaped transactions (two real-account postings / no system posting) and opening transactions (have an `Opening Balances` posting). "Sum the Income system account" is explicitly NOT the reported-income definition.
- **D5 Spend sign/category/necessity.** `spentByCategory` sums POSITIVE `Expenses`-account postings grouped by category. Necessity is copied onto each posting at write time (tx override onto every split posting); category joins stay tenant-scoped by joining the parent transaction's `userId`.
- **D6 Cardinality.** Merchant/biggest-spend/count/report queries use `count(distinct transaction_id)` while summing posting amounts, so a split transaction isn't counted N times.
- **D7 Opening-row visibility.** Opening transactions stay hidden from generic transaction lists/counts/search by detecting the `Opening Balances` posting (replacing the `is_opening` filter). Newly-created opening transactions for card/loan/investment types are hidden the same way — no new visible rows vs. today.
- **D8 Scoping/backup.** `postings` scopes via parent transaction: register in `ALL_TABLES` + `LINKED_TABLES` (`{ fk: "transaction_id", parent: "transactions" }`), NO `postings.user_id`, positioned in `ALL_TABLES` immediately AFTER both `accounts` and `transactions` so both restore paths satisfy FKs. Two DISTINCT surfaces, not conflated: (i) the JSON/encrypted archive round-trips `postings` ROWS (export + restore, with D19 system-account remap); (ii) the human-readable transactions CSV (`backup.ts:121`, export-only, NOT a restore format) is rewritten to derive amount/account/category from postings.
- **D9 System accounts.** Add a dedicated `"system"` value to the account-type pg enum + `system_kind` enum column {`expenses`,`income`,`opening`} nullable; UNIQUE partial index `(user_id, system_kind) WHERE system_kind IS NOT NULL`. Excluded from EVERY generic account query (`listAccounts`, `accountBalancesAtDate`/net worth, bank/cash, AMB, cards, `deleteAccount` used-check). `assertOwnedAccount` (or a new `assertOwnedRealAccount`) REJECTS system-account IDs supplied through the simple transaction API. Guard edit/delete/archive. Idempotent seeding at registration + demo + restore. Restore REGENERATES system accounts and remaps postings (never restores archived system-account IDs).
- **D10 Opening-balance handling.** Replace `planOpeningBalanceChange` with a posting-based equivalent: find the account's opening transaction via its `Opening Balances` posting; update/insert/soft-delete the whole transaction; preserve the effective-date rule (dated before the earliest ordinary transaction); type change no longer moves storage (all types unified). `createAccount` with an `openingBalancePaise` INPUT expands to an opening transaction for ALL types.
- **D11 Reconciliation.** `absorbCarryover` adjusts the canonical opening transaction's postings (card posting −D, `Opening Balances` +D), idempotent (re-derive, apply only remaining delta), preserving the existing account-row lock order and the `Number.isSafeInteger` refusal.
- **D12 Integer-paise safety (AC6).** `assertZeroSum` computes in `BigInt`. Money input schemas use safe-integer validation (`.refine(Number.isSafeInteger)`/`z.number().int()` + safe check). `isSafeInteger` checks after every arithmetic step deriving postings; range-check SQL aggregates before `Number(...)`. Property test generates values near 0 AND near ±`Number.MAX_SAFE_INTEGER`. NEVER proportionally rescale splits — require an exact new allocation or an explicit residual-leg adjustment.
- **D13 Transactional enforcement (AC2).** A single invariant-enforcing writer helper (`postEntry`) wraps header+postings in ONE DB transaction and asserts zero-sum immediately before persistence. EVERY writer routes through it (create, update, bulk, transfer, opening, import commit, recurring fire, review-actions, insurance premium, EPF, demo seed, reconciliation). No posting write exists outside it.
- **D14 SP0 is pure TS.** SP0 = posting-shape helpers + property tests ONLY, no schema/seed change. All schema + system-account seeding + conversions + shared contract + web land atomically in SP1 as a single `0067_*` migration.
- **D15 updateTransaction round-trips.** Separate header patches from posting patches: changing `accountId` moves the real posting; changing `amountPaise` updates both sides preserving exact negation; changing category/necessity updates the system posting(s); changing a split-transaction amount uses a defined policy (reject until splits resubmitted / explicit residual) — never silent rescale. Bulk category actions update all applicable `Expenses`/`Income` postings, never touching transfers/openings.

## Resolved design decisions (from review-2)
- **D16 Transfer merge / unlink identity.** Fresh `createTransfer` and inbox auto-classification produce ONE transfer transaction directly (two non-system postings). `linkTransfer(outTxId, inTxId)` of two PRE-EXISTING ordinary transactions is a MERGE: keep the outflow transaction as the surviving header; migrate the counterpart's children (attachments, `transaction_links`) onto the survivor; replace both transactions' system postings with the two real postings on the survivor; delete the counterpart header. `unlinkTransfer` splits the transfer header back into two ordinary transactions, recreating an `Expenses`/`Income` system posting on each per account-type/sign rules. Card-repayment acceptance (`transfer-classification.ts:233,248`) that reuses an existing paying-side transaction must produce a single transfer header via the same merge, not a second row. Extracted drafts that today store two distinct transaction IDs (`transfer-classification.ts:114,120`) store the one surviving transfer id on both sides. Scope adds web `TransactionDrawer.tsx` and `apps/web/src/lib/queries.ts` (suggestions/link/unlink/record-transfer contracts).
  - **Reference policy (deterministic, prevents dangling refs / silent loss):** a transfer leg is a plain money move, so `linkTransfer` REJECTS (HttpError) if EITHER transaction carries any header-level domain reference — `sipId`, `reconciledStatementId`, `policyId`, `resourceId`, or `recurringTemplateId`. Only child collections migrate to the survivor: `attachments` and `transaction_links`. Consequently the merged transfer header carries none of those domain references, and `unlinkTransfer`'s two recreated ordinary transactions carry none either (attachments/links remain on the surviving/outflow transaction; the recreated inflow starts clean). This keeps merge/unlink total and reversible without redesigning SIP/reconciliation/insurance/resource/recurring linkage.
- **D17 `"system"` account type is DB-INTERNAL.** Add `"system"` ONLY to the Postgres account-type enum; do NOT add it to the public `AccountTypeSchema`. Every generic account query already filters system accounts out (D9), so the existing `as AccountType` projections (e.g. `accounts.ts:173`) only ever see real types. Add a narrowing guard at each DB→public boundary that asserts/filters `system_kind IS NULL` before casting, so a system row can never reach `ACCOUNT_BUCKET`/`ACCOUNT_RETURN_BPS`/web labels or the net-worth exhaustiveness test. No change to `networth.ts`, `goal-returns.ts`, `account-meta.ts`, or `networth.test.ts` enum maps.
- **D18 Writer audit: posting-affecting vs header-only.** `postEntry` governs every INSERT/DELETE or monetary/account/category/necessity mutation of postings. Header-only metadata/FK updates may use a clearly-named header-only helper and must NOT touch postings, but every transaction-mutating file is audited and listed: header-only writers `merchants.ts:57` (merchant rename), `sip-lifecycle.ts:501,515` (sip linkage FK), `reconciliation-writes.ts:129,140` (`reconciledStatementId`). Confirm `sip-lifecycle.ts` predicates don't rely on removed `transactions.accountId/amountPaise` columns; if they do, convert those reads to postings.
- **D19 Restore algorithm (user archive).** Concrete sequence: (1) fresh-account precondition guard ignores `system_kind IS NOT NULL`; (2) delete/retain seeded system accounts deliberately (reverse-order delete must skip them); (3) regenerate exactly one system account per kind for the target user; (4) build `old archived system-account id → new account id` keyed by `system_kind`; (5) rewrite each restored posting's `account_id` through that map before insert; (6) restore real accounts + transactions before postings; (7) never insert archived system-account rows as ordinary accounts. Since postings have no `user_id` (D8), this remap can't ride the generic `restore-user.ts:122` row rewrite — it needs an explicit posting-account remap pass.
- **D20 Transaction-level (non-aggregate) consumers keep per-transaction real-posting semantics.** `prefs.ts` large-transaction alerts (`prefs.ts:85-99`: one alert per transaction, signed real amount, account filter, exclude opening/transfer) select the single real posting per transaction — never sum system postings — so a split yields exactly ONE alert and a transfer yields ZERO alerts (transfers are excluded outright, `prefs.ts:99`; the two real postings must never be counted). Same rule for search/list/detail row-level consumers.
- **D21 Recurring EMI shape (parity-critical).** `recurring.ts` EMI materialization stays TWO separate posting-backed transactions — a negative source-account entry (counts as expense) and a positive liability-account principal entry (counts as neither income nor expense) — each balanced by its own system posting. They must NOT be consolidated into one two-real-posting transfer just because two real accounts are involved. Add to T6.
- **D22 One reusable `SafePaiseSchema`.** Define a single `z.number().int()` + `Number.isSafeInteger` refinement in `@compass/shared` and use it for every money field, rather than per-author refinements. Flip the deliberately-unsafe fixture `account-balances.test.ts:16,27` (`9007199254740993`) from "accepts rounded output" to "asserts overflow refusal."
