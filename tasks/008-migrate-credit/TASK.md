### The new reward earn-rate interface — genuinely new code, redesigned per review-1
Confirmed by grep across the whole repo (`investigation-1.md` §11): **no earn-rate lookup, reward-points-from-spend computation, or similar abstraction exists anywhere today.** `card_details.earn_rate_per_100` (integer, non-null, default 0, documented as reward points per ₹100 spent) is stored and passed straight through to the API DTO; `reward_entries` is a point-*movement* ledger (it does not define a rate); `card_issuer_settings` holds limit/utilization-threshold/reminder-lead-time/mobile-number (also no rate). The roadmap AC — "Reward earn-rate lookup exposed as a documented interface for later reuse" — requires **creating** this, with real tests written test-first (this is new logic, not a move, so `tasks/TDD.md`'s normal test-first rule applies in full, unlike the rest of this task).

**Revision 1's single `earnedRewardPoints(spendPaise, earnRatePer100)` function was a calculator, not a "lookup" — review-1 correctly noted the AC asks for both.** Redesigned as two functions in `rewards.ts`:
- **`getCardEarnRate(db, userId, accountId): Promise<number | null>`** — the lookup half: verifies the account belongs to the user (reusing the same ownership-check pattern as `ownedCardAccount`) and is a credit card, and returns the configured `earn_rate_per_100` integer, or `null` if no `card_details` row exists for that account (distinguishing "no card details configured" from a genuinely-stored `0` rate).
- **`earnedRewardPoints(spendPaise: number, earnRatePer100: number): number`** — the pure calculator half, operating only on already-validated inputs: `points = Math.floor(spendPaise * earnRatePer100 / 10_000)` (₹100 = 10,000 paise). Must **reject** (throw, not silently coerce) negative `spendPaise`, negative `earnRatePer100`, non-integer inputs (`Number.isInteger`), and — the precise safe-integer rule review-2 required, since `Number.isInteger` alone does not guarantee a value is safe to multiply without precision loss — **any input or intermediate value that is not a safe integer**: reject if `!Number.isSafeInteger(spendPaise)`, `!Number.isSafeInteger(earnRatePer100)`, or `!Number.isSafeInteger(spendPaise * earnRatePer100)` (check the product's safety *before* dividing by 10,000, since precision loss happens at the multiplication step, not the division). This function must not silently `Math.abs()` a caller's mistake, since ledger `transactions.amountPaise` stores spend as **negative** and a caller must pass the non-negative magnitude explicitly (parameter named `spendPaise` to signal that convention, not the signed ledger amount).

**Explicit test cases required (test-first, per `tasks/TDD.md`):** zero spend, zero rate, exactly ₹100, spend below ₹100, multiple complete ₹100 units, a remainder above a complete unit, rejection of negative spend, rejection of negative rate, rejection of non-integer inputs, rejection when `spendPaise` or `earnRatePer100` itself exceeds `Number.MAX_SAFE_INTEGER`, and rejection when both inputs are individually safe integers but their **product** is not (e.g. a large but realistic `spendPaise` combined with a large `earnRatePer100` that together exceed `Number.MAX_SAFE_INTEGER` before division) — this last case is the one a single "realistic large-spend" sanity check cannot catch, since it specifically requires choosing inputs whose product, not either input alone, crosses the safe-integer boundary.

**Documented scope limitation (required in the function's own doc comment, not just in this task's evidence):** this is a **simplified base-rate estimate** — it does not model category-specific rates, spend caps, milestone bonuses, point valuation, or expiry (`tasks/10.05-reward-model.md` in the roadmap explicitly plans that full model later). The doc comment states this limitation directly (e.g. "base flat rate only; does not model category rules, caps, or point value") rather than referencing a task filename, since task references in production code go stale; the cross-reference to `tasks/10.06-reward-aware-checkout.md`'s discrepancy (below) belongs in this task's evidence trail, not the code comment.

**Known discrepancy to document, not resolve here:** `tasks/10.06-reward-aware-checkout.md` (phase 10, release 2.3.0 — nine phases away) says the interface should draw from `reward_entries` and `card_issuer_settings`, but the only earn-rate field that exists in the schema today is `card_details.earn_rate_per_100`. This task's functions compute from the field that actually exists; flagged here for whoever designs 10.6, rather than silently building toward a shape that doesn't match today's data. `packages/shared/src/money.ts`'s conventions (integer paise, explicit rounding documentation) are the model to follow; keeping this pair of functions in `modules/credit/services/rewards.ts` (not `packages/shared`) is correct for now since there is no cross-workspace consumer yet.
