**The centrepiece of the release.** Today `buildGoalPlan()` computes each goal's requirement *in isolation* — five goals each confidently asking for ₹20k/month against a ₹40k surplus, with nothing reconciling them. There is no engine that splits real income across competing goals.

Given the surplus (5.1), every goal's requirement, the existing user-defined priority order (`/api/goals/order`) and each goal's horizon, produce a single allocation: how much per goal per month, and what it means for each target date.

The interesting case is the normal one — **underfunding**. When the surplus cannot cover everything the engine must not silently prorate into a plan that quietly misses every goal. It should protect non-negotiables first (emergency fund, near-dated commitments), then allocate by priority, and state plainly which goals slip and by how long.

## Acceptance criteria
- [ ] Allocates surplus across all goals in one pass; per-goal monthly amounts sum to ≤ surplus
- [ ] Respects user priority order and horizon urgency; emergency fund treated as a floor
- [ ] Underfunding reported explicitly — which goals slip, by how many months
- [ ] Over-funding surfaces the choice (pull a goal forward vs. free cash) rather than auto-assigning
- [ ] Existing per-goal `GoalPlan` remains available and unchanged for single-goal views
- [ ] Deterministic, integer paise, unit-tested including zero-surplus and single-goal cases
- [ ] typecheck + lint + test green
