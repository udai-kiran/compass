**Substantially built already — this extends it, and must not rebuild it.** `services/goal-plan.ts` already has `targetAllocation(goalType, monthsToTarget)`: a real horizon-based glide path (≥10y → 75/25 equity/debt, ≥7y → 70/30, ≥5y → 60/40, ≥3y → 40/60, ≥1y → 20/80, under a year → 0/100 to protect capital; emergency funds pinned to 0/100). `buildGoalPlan()` turns that into a recommended monthly contribution, splits it across the mix, and reports the gap against committed SIPs.

**What is missing:** it only ever answers *"what mix should this goal hold today?"*. There is no forward path. Extend it to produce the whole schedule from now to the target date — the mix at each step, the dates the allocation changes, and how the required contribution evolves — so the user sees the journey rather than a single spot reading.

Keep it pure and DB-free like the existing module, so the schedule stays unit-testable. Return the switch points explicitly; a roadmap the user cannot act on is decoration.

## Acceptance criteria
- [ ] Forward schedule from today to target date, with allocation at each step and the dates it changes
- [ ] Derived from the existing `targetAllocation()` — the band thresholds are not duplicated or re-hardcoded
- [ ] Undated goals and emergency funds handled exactly as today (no path to glide)
- [ ] Required contribution shown per step, using existing `projection_settings` return/inflation assumptions
- [ ] Pure and DB-free; unit-tested including a goal that crosses several bands
- [ ] Existing `buildGoalPlan` behaviour and `GoalPlan` consumers unchanged
- [ ] typecheck + lint + test green
