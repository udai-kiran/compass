The revised plan is not implementation-ready. The arithmetic bug is fixed, module placement and expiry convention are correct, but the allocation model still cannot guarantee non-reuse and is unsafe for advisory consumers.

## High

- **`UNIQUE(loss_record_id, setoff_fy)` does not prevent double-use across years.** A ₹100 loss can still have ₹100 allocated in FY 2024-25 and another ₹100 in FY 2025-26; both rows satisfy the proposed uniqueness constraint. Worse, `getNetGainsAfterSetOff()` only says it loads allocations for the target FY, so it would ignore amounts consumed in earlier FYs ([TASK.md](/work/personal/compass/tasks/097-loss-carryforward/TASK.md:73), [TASK.md](/work/personal/compass/tasks/097-loss-carryforward/TASK.md:106)). AC6 and AC7 therefore are not met.

  Availability must be calculated separately by type:

  ```text
  availableSTCL = record.stcl - SUM(stcl_used across all prior/finalized allocations)
  availableLTCL = record.ltcl - SUM(ltcl_used across all prior/finalized allocations)
  ```

  A persisted allocation must atomically lock the loss record, validate both remaining balances, and insert in one transaction. The constraints must be per type; the current AC7 wording, `stcl_used + ltcl_used ≤ original amounts`, could allow STCL to consume an LTCL balance. Declaring concurrent correctness a non-goal conflicts directly with claiming double-use prevention ([TASK.md](/work/personal/compass/tasks/097-loss-carryforward/TASK.md:139), [TASK.md](/work/personal/compass/tasks/097-loss-carryforward/TASK.md:147)).

- **Advance-tax and harvesting estimates should not persist BFLA allocations.** Both downstream features are advisory scenarios whose inputs can change during the FY. Persisting a hypothetical allocation from advance tax, as proposed at line 16, would prematurely consume losses and make later estimates depend on which endpoint happened to run first. The revised advance-tax task itself describes scenario estimates and pure orchestration ([096 TASK.md](/work/personal/compass/tasks/096-advance-tax/TASK.md:8), [096 TASK.md](/work/personal/compass/tasks/096-advance-tax/TASK.md:119)). Harvesting similarly explores unrealized transactions rather than filed outcomes ([098 TASK.md](/work/personal/compass/tasks/098-harvesting-planner/TASK.md:19)).

  For estimates, BFLA should be a pure per-year simulation using opening filed balances minus allocations finalized for earlier years. Persist allocations only when the user confirms an actual filed-return set-off, with an explicit finalized/confirmed state. For an already-finalized target FY, read and apply its stored allocation exactly rather than subtracting it and then recomputing another hypothetical allocation.

- **The blind materialization upsert can invalidate existing allocations.** `materializeCurrentFy()` can recompute a smaller residual after allocation rows already exist, causing allocated amounts to exceed the rewritten source balance ([TASK.md](/work/personal/compass/tasks/097-loss-carryforward/TASK.md:99)). It could also rewrite a loss record after filing confirmation merely because holding events were edited. Re-materialization should be allowed only while the record is unconfirmed and has no finalized allocations, or it must validate the new balance against all allocations in the same transaction. Once a loss is confirmed from an ITR, it should be treated as a filed tax fact rather than continuously derived from the portfolio ledger.

- **The annual result remains inadequate for §234C timing.** `getCapitalGains()` exposes signed, dated slices ([capital-gains.ts](/work/personal/compass/apps/api/src/modules/investments/services/capital-gains.ts:76)), but 13.11 collapses them into annual ST/LT totals. Task 13.10 proposes combining that annual post-set-off result with raw positive gains grouped by `sellDate` ([096 TASK.md](/work/personal/compass/tasks/096-advance-tax/TASK.md:10)). That cannot correctly attribute losses or BFLA to due-date buckets. For example, a December loss must not reduce the liability attributable to a gain realized before June 15 as though the loss already existed then. Section 234C relief depends on when the capital-gain income arose and whether the corresponding tax was paid in the remaining instalments or by March 31. [Official Section 234C](https://www.incometaxindia.gov.in/w/section-234c-12).

  Task 13.10 needs a dated set-off simulation as of every due date, using both positive and negative slices through that cutoff. The annual result is suitable for a year-end advisory total, not the instalment-timing calculation.

## Medium

- **The `consume()` arithmetic is correct, but the policy is not universally “tax-minimizing.”** Each call conserves nonnegative loss and gain correctly, and the LTCL bug is fixed. Using LTCL against LTCG first also preserves flexible STCL. However, after that step, always applying STCL to remaining LTCG before STCG ([TASK.md](/work/personal/compass/tasks/097-loss-carryforward/TASK.md:29)) may consume a loss against a lower-rate or exemption-covered LTCG while leaving higher-rate STCG taxable. The statute allows STCL against either class and LTCL only against LTCG; it does not establish this proposed order. [Official Section 70](https://wmstatic-prd.incometaxindia.gov.in/web/guest/w/section-70-128), [official Section 74](https://www.incometaxindia.gov.in/w/section-74-16).

  Call this a deterministic allocation policy, not a tax-minimizing one, or parameterize allocation using the applicable rate buckets. This matters directly to both advance-tax liability and harvesting benefit estimates.

- **`itr_filed && filed_within_due_date` is computationally fine but semantically too broad.** Computing the conjunction in the service rather than persisting a derived column is correct. Legally, however, the loss must have been determined through a timely return of loss under §139(3); merely filing some ITR on time does not prove the modeled loss was declared and accepted as the carried-forward amount. [Official Section 80](https://www.incometaxindia.gov.in/documents/20117/42998/Section-80_2026-05-05_11-51-34_8cd341_en.pdf/3393d817-0497-950d-4fa0-6ac04bba2679?t=1779691352825&version=2.0), [official Section 139](https://www.incometaxindia.gov.in/documents/20117/42998/Section-139_2025-11-01_09-36-05_a8fe49_en.pdf/8a76ffdb-7d50-c0a4-aeb1-a7e6b0b3b1bc?t=1771315890749&version=1.0).

  Rename the confirmation to something like `loss_return_filed`/`loss_declared_in_itr`, or explicitly state that confirming filing also confirms these stored STCL/LTCL balances match the filed return. Otherwise portfolio-derived amounts can become “eligible” merely by toggling two generic booleans.

- **Allocation order across brought-forward records is unspecified.** Once several eligible origin years exist, the service needs a deterministic oldest-expiring-first policy. Otherwise it could consume a newer loss while an older loss expires, affecting future estimates and `expiringLosses`, even though the current year’s net gain is unchanged. Sort by `expires_fy`, then `origin_fy` and ID, and test that conservation and expiry behavior remain stable regardless of query order.

- **The child `user_id` can disagree with its parent.** The proposed table has independent FKs for `loss_record_id` and `user_id`, but nothing guarantees that both refer to the same user ([TASK.md](/work/personal/compass/tasks/097-loss-carryforward/TASK.md:73)). That can corrupt user-scoped exports or create an allocation visible under one user whose parent belongs to another. Either omit `user_id` and scope/export through the parent, or enforce a composite FK `(loss_record_id, user_id)` to a corresponding unique parent key.

- **The persistence write path is missing from the actual route plan.** The root-cause resolution promises `POST /capital-loss-records/allocate`, but the route list and P4 contain only four endpoints and omit it ([TASK.md](/work/personal/compass/tasks/097-loss-carryforward/TASK.md:16), [TASK.md](/work/personal/compass/tasks/097-loss-carryforward/TASK.md:114)). Advance tax should not fill this role. Either add a user-confirmed final-allocation endpoint and contracts/tests, or remove the allocations table from this advisory task and defer filed allocation history.

- **FY text fields need service-level relationship validation.** The inclusive result is correct: origin FY 2023-24 is usable in the eight succeeding FYs, 2024-25 through 2031-32, and first unusable in 2032-33. [Official Section 74](https://www.incometaxindia.gov.in/w/section-74-16). However, the proposed text columns do not enforce canonical FY labels or relationships. Use `parseFy()` ([financial-year.ts](/work/personal/compass/apps/api/src/lib/financial-year.ts:53)) to derive `expires_fy`, compare numeric start years, and reject allocations where `setoff_fy <= origin_fy` or `setoff_fy > expires_fy`. Do not accept client-computed expiry.

- **Portfolio-only materialization is not a complete filed-loss source.** The current statement covers realized events for Compass holdings and collapses them by term ([capital-gains.ts](/work/personal/compass/apps/api/src/modules/investments/services/capital-gains.ts:51)); it does not include capital gains entered directly in an ITR or held outside Compass. Materialized records should be explicitly marked as estimates until the user confirms or replaces them with filed balances. Otherwise advance tax and harvesting may present incomplete loss availability as authoritative.

## Low

- **`materializeCurrentFy()` contains an irrelevant and incorrectly named step.** It says to load “current-year BF allocations” using `target_fy`, but the proposed column is `setoff_fy`, and BF allocations do not participate in computing the post-CYLA residual that materialization stores ([TASK.md](/work/personal/compass/tasks/097-loss-carryforward/TASK.md:99)). Remove this step; materialization should compute only current-year CYLA.

- **The allocation audit shape is insufficiently explicit for downstream rate analysis.** Storing only aggregate `stcl_used_paise` and `ltcl_used_paise` does not preserve whether STCL was applied to STCG or LTCG. If allocations become filed facts, consider destination columns such as `stcl_to_stcg`, `stcl_to_ltcg`, and `ltcl_to_ltcg`, or persist a validated allocation breakdown. This will prevent 13.10 and 13.12 from reconstructing potentially different allocations later.

- **Tests should cover invalid inputs and separate conservation identities.** `consume()` should reject negative, non-integer, or unsafe-number inputs, and property tests should independently assert STCL and LTCL conservation. The helper’s `losUsed` field is also a typo likely to leak into contracts ([TASK.md](/work/personal/compass/tasks/097-loss-carryforward/TASK.md:32)).

The tax-module placement and relative route convention are correct: tax routes belong in `apps/api/src/modules/tax`, are registered through the tax plugin, and should use paths relative to `/api/tax`, matching the existing plugin and route pattern ([plugin.ts](/work/personal/compass/apps/api/src/modules/tax/plugin.ts:5), [regime-preference.ts](/work/personal/compass/apps/api/src/modules/tax/routes/regime-preference.ts:22)). The Drizzle upsert form is also correct when implemented as `.onConflictDoUpdate({ target: [capitalLossRecords.userId, capitalLossRecords.originFy], set: ... })`; this matches existing tax-service usage ([regime-preference.ts](/work/personal/compass/apps/api/src/modules/tax/services/regime-preference.ts:131)). It must additionally update `updatedAt` and observe the finalized/allocation guards above.
