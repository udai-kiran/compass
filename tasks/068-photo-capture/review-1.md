**Findings**

BLOCKING: FLAG 1 should be revised from store-and-keep to transient store-then-delete, unless 9.5 also adds a durable DB reference and backup integration. The current codebase treats `Storage.put()` keys as metadata that must be persisted somewhere: `Storage` docs say `put` returns a key “persisted alongside the file's metadata” ([storage.ts:15](/work/personal/compass/apps/api/src/lib/storage.ts:15)), ledger attachments store `storedPath` in DB immediately after `storage.put()` ([attachments.ts:86](/work/personal/compass/apps/api/src/modules/ledger/services/attachments.ts:86)), and deletes remove both DB row and object ([attachments.ts:122](/work/personal/compass/apps/api/src/modules/ledger/services/attachments.ts:122)). Backup only includes keys in `FILE_COLUMNS` ([backup.ts:217](/work/personal/compass/apps/api/src/modules/system/services/backup.ts:217)), and unreferenced storage keys are explicitly “orphans” for report-only human cleanup ([backup.ts:277](/work/personal/compass/apps/api/src/modules/system/services/backup.ts:277)). Returning an unreferenced `storageKey` from 9.5 creates intentional permanent orphans that will be omitted from backups and indistinguishable from crashed uploads. The investigation itself points this way: existing pattern is “upload → storage.put() → store returned key in DB,” and for 9.5 the image is “likely transient” with post-parse deletion ([investigation-1.md:261](/work/personal/compass/tasks/068-photo-capture/investigation-1.md:261), [investigation-1.md:265](/work/personal/compass/tasks/068-photo-capture/investigation-1.md:265)). Recommendation: validate and capability-gate first, `storage.put()`, call vision using the in-memory buffer, then `storage.delete(key)` in `finally`; return `storageKey: null` or drop it from the response. If the desired product behavior is later attachment, that later task should add a real table/owner reference and update backup `FILE_COLUMNS`.

BLOCKING: Vision capability gating is too narrow. There is no `supportsVision` flag today; `AiProvider` only has `name`, `enabled`, and methods ([types.ts:256](/work/personal/compass/packages/ai/src/types.ts:256)). Ollama absolutely rejects images before HTTP via `assertNoImages()` ([ollama.ts:79](/work/personal/compass/packages/ai/src/ollama.ts:79), [types.ts:241](/work/personal/compass/packages/ai/src/types.ts:241)), so the plan is right that 9.5 must gate before `chat()`. But `ai.name !== "ollama"` is not a true vision-capability test for all configured providers. `deepseek` is created through the OpenAI-compatible provider with default model `deepseek-chat` ([factory.ts:76](/work/personal/compass/packages/ai/src/factory.ts:76)), and `openrouter` defaults to `deepseek/deepseek-chat` ([factory.ts:67](/work/personal/compass/packages/ai/src/factory.ts:67)); custom OpenAI-compatible models may also be text-only. OpenAI-compatible `chat()` will locally validate image shape, then send an `image_url` data URI ([openai-compat.ts:108](/work/personal/compass/packages/ai/src/openai-compat.ts:108), [openai-compat.ts:153](/work/personal/compass/packages/ai/src/openai-compat.ts:153)); a text-only upstream will reject with a provider 4xx converted to `AiUnavailableError` ([http.ts:308](/work/personal/compass/packages/ai/src/http.ts:308)), which the plan says should propagate as 5xx. That violates the “non-vision provider graceful” goal in [TASK.md:53](/work/personal/compass/tasks/068-photo-capture/TASK.md:53). Revise the plan to introduce or derive a real vision capability in `packages/ai`, or explicitly gate known text-only providers/models. At minimum, `deepseek` must not be treated as vision-capable.

BLOCKING: FLAG 2 is acceptable only if the board AC is explicitly amended/deferred; as written, 9.5 cannot claim done without UI. The board task includes client-side work in the task body ([09.05-photo-capture.md:12](/work/personal/compass/tasks/09.05-photo-capture.md:12)) and has an AC that “Mobile camera capture works; desktop file picker still works” ([09.05-photo-capture.md:16](/work/personal/compass/tasks/09.05-photo-capture.md:16)). It is also true that task 12.1 explicitly owns “Photo capture” UI with `capture="environment"` ([12.01-shopping-lists-ui.md:18](/work/personal/compass/tasks/12.01-shopping-lists-ui.md:18), [12.01-shopping-lists-ui.md:26](/work/personal/compass/tasks/12.01-shopping-lists-ui.md:26)), and 9.2/9.3/9.4 followed a server/shared-contract split. Recommendation: keep UI out of 9.5, but revise 9.5’s acceptance criteria/status text to say the camera/file-picker AC is transferred to 12.1. Without that amendment, the plan is internally consistent but not board-AC complete.

non-blocking: The vision message shape itself is correct. `ChatMessage` supports user `MessageContent` as either string or `ContentBlock[]` ([types.ts:81](/work/personal/compass/packages/ai/src/types.ts:81), [types.ts:147](/work/personal/compass/packages/ai/src/types.ts:147)); `ImageBlock` is `{ type:"image", mediaType, data }` with raw base64 and no data URI ([types.ts:134](/work/personal/compass/packages/ai/src/types.ts:134)). Anthropic shapes this as base64 source data ([anthropic.ts:126](/work/personal/compass/packages/ai/src/anthropic.ts:126)); OpenAI-compatible shapes it as a data URI ([openai-compat.ts:153](/work/personal/compass/packages/ai/src/openai-compat.ts:153)). `assertImagesValid()` enforces media type, canonical base64, and decoded size before HTTP ([types.ts:201](/work/personal/compass/packages/ai/src/types.ts:201)). The plan should add tests asserting the exact block list and no `data:` prefix in `ImageBlock.data`.

non-blocking: The `parse-list.ts` refactor is low risk if it is literally mechanical. Current behavior is `parseItemsFromTurn()` for the three-way tool/prose discipline ([parse-list.ts:118](/work/personal/compass/apps/api/src/modules/shopping/services/parse-list.ts:118)), then normalize and blank-filter inside the caught parse step ([parse-list.ts:214](/work/personal/compass/apps/api/src/modules/shopping/services/parse-list.ts:214), [parse-list.ts:230](/work/personal/compass/apps/api/src/modules/shopping/services/parse-list.ts:230)). Extracting `itemsFromTurn(turn, structured)` should preserve the same `try/catch`, empty messages, and blank-name filter. Existing 9.4 tests should still hold if `parseItemsFromTurn` remains exported and unchanged.

non-blocking: Size/type enforcement is directionally right, but the plan should specify the limit-error handling path. `MAX_IMAGE_BYTES` is 5 MB decoded bytes ([types.ts:126](/work/personal/compass/packages/ai/src/types.ts:126)), and using it as upload limit is sensible because larger images cannot be sent to the model. Multipart routes use `req.file({ limits: { fileSize, files: 1 } })` ([attachments.ts route:27](/work/personal/compass/apps/api/src/modules/ledger/routes/attachments.ts:27)). `@fastify/multipart` can throw `RequestFileTooLargeError` with 413; the global error handler will pass non-5xx errors through ([app.ts:239](/work/personal/compass/apps/api/src/app.ts:239)). If you want a curated message, mirror backup restore’s `file.file.truncated` check after streaming ([backup.ts:87](/work/personal/compass/apps/api/src/modules/system/routes/backup.ts:87)) or catch multipart’s 413 and rethrow `HttpError(413, "...5 MB...")`. The JPEG/PNG/WEBP allowlist plus magic-byte check mirrors attachments ([attachments.ts:33](/work/personal/compass/apps/api/src/modules/ledger/services/attachments.ts:33), [attachments.ts:53](/work/personal/compass/apps/api/src/modules/ledger/services/attachments.ts:53)). No image URL is accepted, so SSRF is not introduced; no decompression is performed, so image-bomb risk is bounded by byte size and provider-side decode.

non-blocking: Reusing `shopping_parse` is correct. The enum already contains it in API schema ([schema.ts:60](/work/personal/compass/apps/api/src/modules/automation/schema.ts:60)) and shared schema ([ai-events.ts:4](/work/personal/compass/packages/shared/src/schemas/ai-events.ts:4)). Photo parse is the same semantic event as paste parse; use the title/source text to distinguish it. No migration is warranted for a new event kind.

non-blocking: AC4 does not need a new dual-backend storage test in 9.5. The storage contract test already exercises disk and S3 when explicitly enabled ([storage.test.ts:140](/work/personal/compass/apps/api/src/lib/storage.test.ts:140)), and `createStorage` is the single backend selector ([storage.ts:111](/work/personal/compass/apps/api/src/lib/storage.ts:111)). 9.5 should mock/stub `Storage` and assert the service calls `put()` with the exact buffer/content type; if adopting transient lifecycle, also assert `delete()` is called in success and provider-error paths after a successful `put()`.

non-blocking: No AI SDK/convention issue in the plan. Provider wire code lives in `packages/ai`; API code should only build `ChatMessage` blocks and call `ai.chat()`. Existing imports use `.ts` extensions in API modules, so new relative imports should follow that. The route path should remain relative under `/api/shopping`, matching [plugin.ts:12](/work/personal/compass/apps/api/src/modules/shopping/plugin.ts:12) and [capture.ts:2](/work/personal/compass/apps/api/src/modules/shopping/routes/capture.ts:2). Auth/demo behavior is covered by the global chokepoint for non-public mutating routes ([auth.ts:58](/work/personal/compass/apps/api/src/plugins/auth.ts:58), [auth.ts:66](/work/personal/compass/apps/api/src/plugins/auth.ts:66)).

**Verdict**

The plan needs revision before implementation. The two hard changes are: replace store-and-keep with transient storage cleanup unless adding durable DB/backup ownership, and fix vision capability detection beyond `ai.name !== "ollama"` so DeepSeek/OpenRouter-default/custom text-only models do not turn into provider 5xxs. The UI deferral is reasonable for this codebase, but the 9.5 board AC must be explicitly transferred/amended to 12.1 before calling 9.5 complete.
