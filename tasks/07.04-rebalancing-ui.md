> **Read [`UI.md`](./UI.md) first** — stack, the components that already exist, the three-edit nav rule, and the conventions this repo enforces. Do not add a UI or charting library.

**Files:** new `src/routes/goals/RebalancePanel.tsx`, `src/routes/goals/rebalance-view.ts` (+ `.test.ts`).

Turn drift into instructions: which leg is overweight, by how much in rupees, and the switch that corrects it — with **contribution redirection presented first** as the zero-tax route, and corpus switching only where redirection cannot close the gap.

Show the **realised-gain consequence next to every switch that sells** (6.7), clearly labelled as holding-period consequence rather than a final tax figure — the full tax engine does not exist until 2.4.0, and the UI must not imply otherwise.

**The panel must be able to recommend doing nothing.** When the tax consequence outweighs the drift, that is the correct answer and it should be stated as confidently as any other. A rebalancing UI that always finds something to do is generating churn.

Near-goal de-risking (from the 5.1 glide path) appears as a **dated upcoming schedule**, not as a drift alert that surprises the user a month before the goal matures.

## Acceptance criteria
- [ ] Drift shown as amounts per leg, never a boolean
- [ ] Contribution redirection presented before corpus switching
- [ ] Realised-gain consequence beside each selling switch, labelled as such, not as final tax
- [ ] "No action needed" is a first-class outcome, not an empty state
- [ ] Upcoming de-risking steps shown as a dated schedule
- [ ] Cash held in an emergency fund never flagged as drift
- [ ] typecheck · lint · test · `npm run build -w apps/web` all pass
