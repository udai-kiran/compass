## High

- **The member-ID key cannot be populated by the proposed payslip import, and its nullable uniqueness does not work.** The new column is nullable and the import route accepts only `payslipId`, but existing payslips contain only `employerName`; they have no EPFO Member ID field ([tax schema](/work/personal/compass/apps/api/src/modules/tax/schema.ts:79), [shared contract](/work/personal/compass/packages/shared/src/schemas/tax.ts:129)). PostgreSQL’s ordinary `UNIQUE` treats `NULL` values as distinct, so repeated imports with a null ID can create duplicates, while the proposed service-layer fallback is race-prone and cannot serve as the `ON CONFLICT` target ([TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:43), [TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:67)). Require the EPFO Member ID during import/confirmation—either add it to payslip review or accept it in the import request—and make it non-null before relying on `UNIQUE (user_id, wage_month, member_id)`. A partial unique `payslip_id` constraint/FK is also needed if idempotency is expressly “by payslip ID.”

- **H2 remains internally contradictory and is not fixed at the extraction source.** The core decomposition is correct: employer EPF is the part credited to the PF corpus, EPS is the diverted pension portion, and gross employer contribution is their sum. However, the plan incorrectly says employer EPF “goes to 80C projection” ([TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:14)), calls the excluding-EPS amount “gross” ([TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:47)), and later correctly says it is not 80C eligible ([TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:76)). Worse, the current parser still requests “Employer PF (12% basic)” and EPS separately, which can produce exactly the double counting H2 was meant to prevent ([payslip-parse.ts](/work/personal/compass/apps/api/src/modules/tax/services/payslip-parse.ts:288)). Add that parser/prompt to the modified files and define `employer_epf` as the net amount credited after EPS diversion.

- **“Sum = 12% of wage” must not be enforced as an unconditional invariant.** The arithmetic invariant should only be `grossEmployerPaise = employerEpfPaise + epsPaise`. Validating that against 12% requires an explicit EPF-wage base, which the proposed row does not store, and EPFO documents exceptions such as 10% contribution-rate establishments and pension-diversion limits. The task currently promises service enforcement and testing against a nonexistent wage input ([TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:72), [TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:125)). The official EPFO explanation supports the credited-plus-diverted decomposition but not an unconditional 12%-of-arbitrary-wage validation ([EPFO FAQ](https://www.epfindia.gov.in/site_en/FAQ.php/Resource/site_docs/PDFs/Downloads_PDFs/Feedback.php)).

- **The dual-column shape is directionally correct, but reconciliation behavior remains underspecified.** Separate expected and actual values solve H1 structurally. The plan still does not define whether “actual is null” means any component or every component, whether omitted components are zero or unknown, how partial confirmations behave, the grace-period duration/as-of date, zero-denominator mismatch handling, or whether the 1% comparison is per component or over a total ([TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:52), [TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:61), [TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:127)). Since `reconciliation_status` is persisted while gap status is described as time-dependent and “pure computed,” it can also become stale. Define a pure reconciliation function with explicit component, zero, partial, grace-period, and rounding rules; preferably derive status rather than persist it.

## Medium

- **Corpus-only projection is the correct H3 scope, but the proposed projection is not yet sufficiently specified.** Descope of the EPS defined-benefit pension is correct, and projecting only the EPF corpus is adequate. The route nevertheless has no account identifier despite multiple EPF accounts being possible, while the output says the opening corpus comes from an account balance ([TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:89), [TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:107)). The plan also omits retirement age, projection start date, future monthly contribution assumptions, contribution growth, compounding/annual-credit convention, and missing-DOB behavior. Specify an owned `accountId` of type `epf` and either model future credited contributions or explicitly label the result as “current corpus only, no future contributions.”

- **VPF cannot currently be imported as specified.** The table has `expected_vpf_paise`, and AC6 uses VPF, but `CanonicalComponentKindSchema` has no `vpf` kind ([TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:49), [tax.ts](/work/personal/compass/packages/shared/src/schemas/tax.ts:75)). Import logic only maps employee EPF, employer EPF, and EPS ([TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:78)). Either add and parse a `vpf` canonical kind, or remove the claim that payslip import populates a separate VPF value. The actual-entry contract must also clarify whether the passbook’s employee share is entered inclusive or exclusive of VPF to prevent double counting.

- **Import validation and source linkage remain incomplete.** The plan now correctly says to sum multiple `currentPaise` component rows, but still does not specify rejection of negative/unsafe amounts or absent-kind zero-versus-unknown behavior. `payslip_id` is shown merely as `UUID`, not as a foreign key ([TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:50)). It should reference `payslips(id)` with deliberate deletion semantics. The upsert must update only expected/source/display fields and preserve already-confirmed actual values.

- **The identity concept is correct, but the name conflates UAN and Member ID.** Employer name is correctly display-only, and the EPFO Member ID is the appropriate employment/establishment-specific identity for this monthly key. UAN is the employee-level umbrella identifier, not an employer-specific member ID. Prefer `epfo_member_id` or store `uan` and `member_id` separately. Once Member ID is required, `UNIQUE (user_id, wage_month, member_id)` is correct for the single-row expected/actual model.

- **The 80C mapping is correct only in the later invariant and AC6.** Employee EPF plus VPF is the 80C-eligible amount; employer EPF and EPS are not. This is subject to the old-regime aggregate Section 80C cap. Because this task now promises only classification metadata rather than integration into an 80C calculator, AC6 is adequate after correcting the contradictory statement at line 14 and specifying whether eligible amounts come from expected or confirmed actual values.

## Low

- **The document contradicts itself about import conflict behavior.** The review-findings section still says `ON CONFLICT DO NOTHING` ([TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:19)), while the operative import plan correctly says `DO UPDATE` ([TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:83)). `DO UPDATE` is the right choice because re-import must refresh reviewer-corrected expected components, but the stale statement should be removed.

- **The table must be added to both backup collections.** AC7 is correct: because `epf_contributions` has its own `user_id`, it belongs in both `ALL_TABLES` and `USER_TABLES`, not `LINKED_TABLES` ([backup.ts](/work/personal/compass/apps/api/src/modules/system/services/backup.ts:32), [backup.ts](/work/personal/compass/apps/api/src/modules/system/services/backup.ts:55)). If `payslip_id` becomes an FK, place it after `payslips` in `ALL_TABLES` so restore is parent-first. The existing backup coverage test will enforce inclusion.

- **The decomposition update must include more than the numeric count.** Add `epfContributions` to `taxResidents` and increase the expected table count from 76 to 77 ([schema.decomposition.test.ts](/work/personal/compass/apps/api/src/db/schema.decomposition.test.ts:84), [schema.decomposition.test.ts](/work/personal/compass/apps/api/src/db/schema.decomposition.test.ts:125)).

**Verdict:** H3 and the core expected/actual approach are conceptually resolved, and `DO UPDATE`, Member ID identity, 80C classification, and backup inclusion are the right directions. The plan is not implementation-ready until the nullable/unpopulated identity key, parser semantics, reconciliation rules, and projection inputs are made executable and internally consistent.
