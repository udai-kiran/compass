## High

- **The proposed table cannot perform payslip-to-passbook reconciliation.** Each row has only one `source_kind`, while the uniqueness key permits only one row per user/month/employer. Importing the payslip therefore creates the very “contribution record” whose absence is supposed to indicate a gap, and a later passbook entry either conflicts with it or overwrites the expected value. Expected payslip amounts and actual deposited amounts need separate records/tables—or separate expected/actual columns linked by a reconciliation entity. As written, “matched,” “gap,” and “mismatch” cannot be derived reliably. See [TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:29) and [TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:50).

- **Employer EPF/EPS semantics are ambiguous and can double-count contributions and projections.** The canonical names are correct: `employee_epf`, `employer_epf`, and `eps` exist in the schema. However, the parser asks for “Employer PF (12%)” and EPS separately while describing EPS as a diversion from that employer share. The task likewise stores `employer_paise` plus `eps_paise` without defining whether employer EPF is gross before EPS or net after EPS. If it is gross, adding EPS double-counts; if net, the extraction prompt is misleading. Existing ledger code currently adds all three fields, increasing the risk of inconsistent semantics. The plan must establish one invariant, preferably `gross employer contribution = employer EPF credited + EPS diverted`, and test it. See [payslip-parse.ts](/work/personal/compass/apps/api/src/modules/tax/services/payslip-parse.ts:288), [TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:35), and [existing ledger service](/work/personal/compass/apps/api/src/modules/ledger/services/epf-contributions.ts:46).

- **The EPS “benefit projection” is not sound with the proposed inputs.** EPS is a defined-benefit pension, not a corpus grown by the EPF interest rate. The official formula uses pensionable salary and pensionable service divided by 70, with service/date/eligibility rules; EPFO’s calculator also requires dates of joining/exit and treats service up to age 58. The repository has only DOB—no employment/service-history fields—and monthly contribution alone is insufficient for higher-pension and historical-rule cases. The plan needs explicit pensionable-service periods, pensionable salary assumptions, eligibility/rounding rules, and separate EPF-corpus and EPS-monthly-pension outputs. [EPFO pension formula](https://www.epfindia.gov.in/site_docs/PDFs/PQ_PDFs/PQ_BudgetSession1_2020_LS_English.pdf), [official EPFO calculator](https://www.epfindia.gov.in/EP_Cal/pension.html).

## Medium

- **`UNIQUE (user_id, wage_month, employer_name)` is not a safe employer identity.** It allows simultaneous employers only when their names differ exactly. Names can vary between payslip and passbook, the same legal employer can have multiple EPFO establishments/member IDs, and PostgreSQL permits multiple rows where nullable `employer_name` is `NULL`. Conversely, it blocks two source observations for the same employer, which reconciliation requires. Use an owned EPF account/member/establishment identity—such as `account_id` plus establishment/member identifier—with source-specific idempotency constraints. Employer name should be display data, not the key. The existing payslip table has the same nullable-name limitation, so copying its key would reproduce it. See [TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:46) and [tax schema](/work/personal/compass/apps/api/src/modules/tax/schema.ts:88).

- **The plan assumes a nonexistent `retirementDetails.epfBalancePaise`.** `retirement_details` is keyed by `accountId` and contains `annualRateBps`, `referenceNumber`, and `epsBalancePaise`; the EPF corpus is represented by the associated account balance. There may be multiple EPF accounts, so the projection route needs an account identifier and ownership/type validation. See [protection schema](/work/personal/compass/apps/api/src/modules/protection/schema.ts:33).

- **The plan does not integrate with the existing EPF ledger flow.** Compass already exposes `POST /api/epf-contributions`, creates a retirement-account transaction, and therefore changes the account balance. The proposed tax-domain CRUD has no `account_id` or `transaction_id`, so manual/payslip imports could create an unlinked second ledger that neither updates the EPF balance nor prevents duplicate accounting. Scope must define whether the new record replaces, links to, or atomically creates the existing ledger transaction, including rollback and deletion behavior. See [ledger route](/work/personal/compass/apps/api/src/modules/ledger/routes/transactions.ts:54) and [ledger service](/work/personal/compass/apps/api/src/modules/ledger/services/epf-contributions.ts:27).

- **Import logic is only partially correct.** Filtering an accepted, user-owned payslip by the three canonical kinds and reading `currentPaise` is correct; `ytdPaise` must not be used. But the plan does not say to sum multiple rows of the same canonical kind, reject or normalize negative values, treat absent components as zero versus unknown, or make repeated imports idempotent by `payslipId`. It must also re-read reviewer-corrected components—the accepted rows are mutable during acceptance—rather than inferred headers. See [component schema](/work/personal/compass/apps/api/src/modules/tax/schema.ts:118) and [TASK.md](/work/personal/compass/tasks/091-epf-passbook/TASK.md:51).

- **The passbook half of the feature is missing from the scope.** The objective promises passbook reconciliation, and `source_kind` lists `passbook`, but there is no passbook import/manual-confirmation route, passbook source identifier, deposit/credit date, establishment/member ID, or test proving an actual deposit matches an expected payslip amount. Without that, this is payslip aggregation and manual entry, not passbook reconciliation.

- **Gap and mismatch rules are underdefined.** “No record matching it” must specify employer/account matching, how long after wage month a contribution remains pending before becoming a gap, and whether gaps are persisted or calculated. “Differs by >1%” needs a denominator, zero handling, per-component versus aggregate comparisons, and integer rounding rules. A Boolean `gap_flag` alongside a status containing `gap` can also drift unless one is derived or DB-constrained.

- **The interest-rate approach is acceptable only after correcting the data source and labeling.** A pure last-known-rate projection is reasonable for an advisory estimate if the result exposes the exact rate, applicable FY, whether it was recommended or officially notified, and that the same rate is extrapolated. But `tax-rules.ts` currently contains income-tax rules only—no EPF interest series—and the plan’s “currently FY 2023-24” statement is stale. The latest official approval found is 8.25% for FY 2024-25, while CBT recommended 8.25% for FY 2025-26 on March 2, 2026. Store effective-dated EPF rates separately instead of silently extending the income-tax rules module. [FY 2024-25 approval](https://www.pib.gov.in/PressReleaseIframePage.aspx?PRID=2209767&lang=2&reg=48), [FY 2025-26 recommendation](https://www.pib.gov.in/PressReleasePage.aspx?PRID=2234502&lang=1&reg=3), [tax-rules.ts](/work/personal/compass/apps/api/src/lib/tax-rules.ts:1).

- **Projection parameters remain unspecified.** DOB exists, but retirement age does not. The plan should define or request the EPF/EPS retirement age, contribution-growth assumption, projection start date, handling of historical/future contributions, EPF’s annual credit mechanics, and behavior when DOB/account balance/service history is missing. See [user profile schema](/work/personal/compass/apps/api/src/modules/system/schema.ts:32).

- **AC4 does not name an actual 80C integration point.** The table and shared schema alone do not make employee EPF plus VPF “feed 80C.” No tax aggregation service is included in modified files or tests. Either add the relevant deduction computation and old-regime/cap tests or narrow AC4 to classification metadata.

## Low

- **`employer_pan` is not present on payslips**, so import-from-payslip cannot populate it. Also, PAN is not necessarily the best EPFO establishment identity; an establishment/member identifier is more useful for reconciliation.

- **Schema invariants are missing.** Monetary columns should be nonnegative, status/source values should use enums or checks, `source_id` should be required for payslip rows, and paise values exposed as JavaScript numbers should be constrained to safe integers.

- **`gap_flag` duplicates `reconciliation_status='gap'`.** Keeping both persisted creates avoidable inconsistent states; derive the Boolean in the response unless a justified indexed flag is required.

- **The test plan omits key cases:** duplicate imports/concurrency, multiple component rows, two simultaneous employers, null/variant employer names, expected-versus-actual source pairing, cross-user account/source isolation, multiple EPF accounts, missing projection inputs, and gross-versus-net employer/EPS invariants.
