**The decision that contains the blast radius.** A full double-entry API would force every caller — the web app, the import pipeline, the inbox — to think in legs. Most of the time there is nothing to think about: money left a bank account and it was groceries.

So keep the familiar shape working. `POST /api/transactions { accountId, amountPaise, categoryId }` continues to be valid and **internally expands to two postings** (the asset leg, and the `Expenses`/`Income` counter-leg carrying the category). Only genuinely multi-leg cases need the new shape.

Add an explicit postings payload alongside it for the cases that need it — splits, transfers, and anything with more than two legs — and expose postings on reads so the web app can show both legs of a transfer without a link table.

This keeps `apps/web` almost entirely unchanged through the conversion, which is what makes a ledger-core rewrite survivable in one release.

## Acceptance criteria
- [ ] Existing single-account create/update payloads still valid and still produce balanced postings
- [ ] Explicit multi-posting payload accepted for splits, transfers and N-leg transactions
- [ ] An unbalanced explicit payload is rejected with a clear error naming the imbalance
- [ ] Reads expose postings; a transfer shows its counterpart account without a link table
- [ ] Route-table snapshot from 0.3 updated deliberately, with schema changes reviewed
- [ ] `apps/web` requires no change beyond typed schema updates for the common paths
- [ ] typecheck + lint + test green
